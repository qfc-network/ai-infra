# 字节跳动 Seed 与豆包：消费级规模下的 AI 基础设施

- **机构**: 字节跳动 / Seed 研究院（seed.bytedance.com）
- **核心论文**: MegaScale（NSDI 2024）、HybridFlow/verl（arXiv:2409.19256）、Seed1.5-VL（2025）
- **产品线**: 豆包（Doubao）大模型家族——豆包专业版、豆包轻量版、豆包视觉版、Seed1.5-Thinking
- **相关链接**: [MegaScale 论文](https://arxiv.org/abs/2402.15627) · [verl 仓库](https://github.com/volcengine/verl) · [Seed1.5-VL](https://arxiv.org/abs/2505.07062)

## 核心摘要

字节跳动通过豆包运营着全球规模最大的大模型推理集群之一，豆包已深度集成于抖音平台并与微信展开竞争。Seed 研究院产出了两项重要的基础设施成果——**MegaScale**（12,288 卡规模下的容错大模型训练系统）和 **verl/HybridFlow**（异构并行 RLHF 训练框架）——以及豆包和 Seed1.5 系列模型。字节跳动基础设施建设的独特之处在于：其优化目标是**消费产品规模下的推理成本与吞吐量**，而非单纯的评测分数，且整个过程受到出口管制的硬件约束。

## 背景：字节跳动作为基础设施实验室

字节跳动以抖音（TikTok）母公司闻名，但 Seed 研究院在 AI 系统研究领域是不容忽视的重量级参与者。其组织逻辑颇为特殊：与 OpenAI 或 Anthropic 以模型 API 为核心产品不同，字节跳动是用大模型来驱动一个已拥有 10 亿以上日活跃用户的消费平台。这一差异决定了所有基础设施优先级的走向。

影响是直接且具体的：

**推理成本是第一优先级。** 在每日超 1 亿次请求的量级下，推理栈每提升 1% 的效率，意味着数千万美元的年化节省。字节跳动在 FP8 量化、推测解码、KV 缓存压缩和前缀缓存上的持续投入，动机不是学术兴趣，而是立竿见影的经营收益。

**时延 SLO 要求严格。** 豆包是嵌入抖音和其他消费应用的对话与语音产品，用户期望亚秒级的首 token 延迟。这一需求推动字节跳动较早部署了激进的预填充-解码分离架构和连续批处理。

**硬件供给受限。** 2022 年 10 月起，美国出口管制将字节跳动等中国 AI 实验室列入实体清单，禁止进口 H100 和 A100（80GB 版）。字节跳动已囤积 H800——NVIDIA 面向出口管制设计的 H100 合规变体——以及老款 A100（40GB），同时在评估华为昇腾 910B 作为国产替代方案。

**监管合规成本真实存在。** 中国 AI 法规要求在部署环节嵌入内容审核与价值对齐层，这是字节跳动必须大规模运营、而西方同等体量的实验室无需承担的一层工程开销。

verl 框架和 MegaScale 论文正是这些压力的直接产物：持续运营 12,000 卡集群，你就必须构建容错的训练基础设施；在 70B+ 规模上做有竞争力的模型后训练，你就必须构建灵活高效的 RLHF 基础设施。

## MegaScale：12,288 卡规模下的容错训练

MegaScale（NSDI 2024）是字节跳动公开发表的、关于在 12,288 卡集群上训练 175B+ 参数大模型的系统工作。这本质上是一篇**运维与可靠性论文**，而非模型架构论文——其核心贡献在于揭示：在这一规模下，硬件故障和性能抖动才是训练效率的主要瓶颈，而解决这些问题需要专门的基础设施设计。

### 故障问题的量化

MegaScale 的核心数据点：

> 在 12,288 卡规模下，字节跳动报告每约 **20 分钟发生一次硬件故障**。

这并非设备质量低劣导致，而是概率规律的必然结果。12,288 块 GPU、6,144 条互联链路，以及每个节点对应的 CPU、内存、NVMe 组件，即便单组件的平均无故障时间（MTBF）长达数年，整集群的 MTBF 也只有分钟量级。若采用朴素的"每 30 分钟写检查点、故障后从头恢复"方案，约 30% 的训练时长将消耗在恢复流程上。

MegaScale 的容错机制直接针对这一问题：

**内存检查点。** MegaScale 不在训练过程中将检查点刷写到分布式存储（这会引入 GPU 空闲等待），而是在训练继续推进的同时，将检查点**异步复制到 CPU DRAM**。GPU 流水线不暂停；检查点在下一个训练步计算期间并行物化到 CPU 侧。故障发生时，从 CPU DRAM 读取恢复（快速），而非从分布式存储读取（缓慢）。这将检查点引入的训练空闲时间从约 3% 降至接近零。

**慢节点检测与迁移。** 在流水线并行训练中，最慢的那个 stage 决定整条流水线的吞吐量。一个仅运行在额定性能 90% 的节点会成为永久瓶颈。MegaScale 在集合通信操作（AllReduce、AllGather）期间测量每个 rank 的耗时，识别持续偏慢的节点，并将流水线 stage 分配重新映射，将工作量移离慢节点。关键机制在于：**仅重启受影响的 PP stage**，而非整个作业。这将恢复时间控制在秒级而非分钟级。

**局部恢复范围。** 当某块 GPU 故障时，MegaScale 仅重启该节点上的流水线 stage，健康的 stage 在同步屏障处等待，故障 stage 从最近的内存检查点重载后恢复。这需要跨流水线 stage 精心设计屏障协调逻辑，但将恢复代价控制在与受影响集群比例相当的量级，而非全局重启。

### 通信优化

MegaScale 用**模型浮点利用率（MFU）**衡量训练效率，即实测吞吐与理论峰值算力之比。报告数据：在 12,288 卡规模上训练 175B 模型，**MFU 达到 55.2%**，与同等硬件配置下 Megatron-LM 的数据相当。

| 并行维度 | MegaScale 方案 | 效果 |
|---|---|---|
| 张量并行（节点内） | 节点内优先走 NVLink 的 TP，典型 TP=8 | 高带宽集合通信保留在节点内 |
| 流水线并行（跨节点） | 跨节点走 InfiniBand 的 PP | 降低跨节点 AllReduce 数据量 |
| 数据并行 | PP 副本间的外层 DP | 扩大 batch size；梯度 AllReduce 与计算重叠 |
| AllReduce 重叠 | CUDA stream：反向传播与梯度 AllReduce 并发 | 用计算掩盖通信延迟 |

分层 AllReduce 的设计——节点内走 NVLink，节点间走 InfiniBand——在大规模训练中已是通行做法，但 MegaScale 针对其 IB 网络拓扑专门调优了自定义集合通信库：节点内采用环形 AllReduce，跨节点采用递归折半加倍，并对 rank 排布进行拓扑感知优化以最小化 IB 跳数。

MFU 计算公式：

$$\text{MFU} = \frac{\text{实测吞吐（tokens/s）} \times 6ND}{\text{峰值 FLOP/s} \times \text{GPU 数量}}$$

其中 $N$ 为模型参数量，$D$ 为训练序列长度，系数 6 对应标准近似下的前向与反向传播 FLOPs（每个乘加 2 FLOP，反向再乘 3）。在 175B 参数下达到 55.2% MFU，意味着 MegaScale 从理论硬件上限中提取了可观的比例——与 100% 的差距来源于通信开销、访存瓶颈操作以及残余的慢节点效应。

## 豆包模型家族

豆包（Doubao）是字节跳动的消费级大模型产品线，主要面向中国市场，通过豆包 App 部署，并集成于抖音、字节企业工具以及火山引擎（字节旗下云平台）。模型家族按成本/质量分层：

**豆包专业版**：面向复杂任务的全能力前沿模型，覆盖代码、长文本推理、文档分析。主要通过火山引擎 API 服务企业和专业用户。

**豆包轻量版**：更小、更快、更低成本的变体，面向高吞吐消费场景——对话、内容生成、简单问答。是豆包消费级对话界面背后的主力模型。

**豆包视觉版**：处理图片和视频帧的多模态变体，集成于抖音内容处理流程。

**Seed1.5-VL**：字节跳动 2025 年发布的视觉语言研究模型。架构遵循 LLaVA 范式（参见 `../../multimodal/llava/`）：ViT 编码器将图像处理为图块嵌入，MLP 投影器将视觉特征对齐到大语言模型的 token 嵌入空间，豆包大模型主干处理融合后的序列。Seed1.5-VL 在 OpenCompass 和 MMBench 多模态基准上具有竞争力，在图表理解、文档 OCR 和视频帧描述任务上表现突出。

**Seed1.5-Thinking**：推理专项模型，通过 GRPO 进行后训练（参见 `../../foundational/grpo/`）。设计目标是在数学、代码和形式化推理基准上与 DeepSeek-R1 和 Qwen3 竞争。选择 GRPO 而非 PPO，与 DeepSeek-R1 的设计决策一致：GRPO 去掉了 Critic 模型，降低了后训练期间的显存压力。在 70B+ 规模下，这一差异意义重大——Critic 模型与 Policy 模型需要等量的 HBM，去掉它可以释放足够的显存来增大 batch size 或序列长度。verl 框架（`../../foundational/verl/`）是这条后训练流水线的基础设施支撑。

规模背景：豆包**每日服务数亿次查询**，覆盖消费级和企业级部署。这一量级将字节跳动与 OpenAI、Google、Meta 并列于极少数每提升一个百分点的推理效率都具有直接财务意义的组织行列。

## verl / HybridFlow：核心基础设施贡献

verl（火山引擎强化学习框架）起源于字节跳动 Seed，详细介绍见 `../../foundational/verl/`。在理解字节跳动基础设施取向时，以下要点值得关注：

核心洞察是：RLHF 和 GRPO 训练需要**同时运行四个模型**（策略模型、参考模型、奖励模型、Critic 模型），而每个模型都有不同的最优并行配置。70B 策略模型需要宽张量并行来保证生成吞吐量；7B 奖励模型则受益于宽数据并行来保证评分吞吐量。强迫它们共用同一套 TP/DP 配置，会同时浪费互联带宽和 GPU 算力。

verl 的 HybridFlow 架构将 RL 控制循环（单 Python 进程）与分布式执行（每个模型在自己的 worker group 中以独立的 TP/PP/DP 配置运行）分离。结果：在 70B 规模下，**相比 OpenRLHF 吞吐提升 1.4 倍，相比 TRL 提升 2.1 倍**，rollout 阶段 GPU 利用率从串行单模型方案的 43% 提升至 82%。

实践意义：verl 是 Seed1.5-Thinking 在字节 H800 集群上以合理成本完成 GRPO 后训练的基础设施前提。它同时也是让外部实验室能够复现 DeepSeek-R1 式训练、而无需自建专有基础设施的关键框架——这或许是 verl 影响最广泛的贡献。

## 字节跳动规模下的推理基础设施

### 服务栈架构

字节跳动豆包的生产推理栈没有公开详细文档，但从已发表工作和行业观察中可以梳理出大致轮廓：

**PagedAttention + 连续批处理**：标准的 vLLM 式 KV 缓存内存管理。在豆包的请求量级下，PagedAttention 所解决的 KV 缓存碎片问题至关重要——若没有它，在长上下文下服务大批次请求需要大幅过量供应 GPU 显存。

**FP8 量化推理**：字节跳动以 FP8 精度服务豆包模型（H800 和 H100 硬件均支持）。FP8 相比 BF16 将访存带宽需求减半，而访存带宽正是解码阶段服务的主要瓶颈。自回归解码的访存带宽约束可表示为：

$$\text{每 token 延迟} \approx \frac{\text{模型大小（字节）}}{\text{总 HBM 带宽（字节/秒）}}$$

70B 模型 BF16 精度下，每个解码步需读取 140 GB 参数；FP8 下降至 70 GB。H800 HBM 带宽 3.35 TB/s，对应小批次下的每 token 延迟下界从约 42 ms 降至约 21 ms，再叠加批处理收益。

**预填充-解码分离（PD 分离）**：字节跳动是分离式推理服务的早期采用者，将计算密集的预填充阶段（提示词处理）与访存带宽瓶颈的解码阶段（token 生成）分配到独立的 GPU 池上。该架构与 DistServe 和 Mooncake 类似（参见 `../../foundational/distserve/`），允许两个阶段独立扩缩容：当提示词流量激增时，扩充预填充容量；当持续生成负载增加时，扩充解码容量。在字节跳动的规模下，核心运营收益是两个 GPU 池的利用率都得到提升——预填充是算力瓶颈，解码是带宽瓶颈；将二者混部在同一批 GPU 上只能对两者都形成妥协。

**前缀缓存**：豆包的消费场景涉及大量提示词复用——系统提示、模板前缀、重复出现的上下文窗口。前缀缓存（参见 `../../foundational/prefix-caching/`）避免对跨请求共享的前缀重复计算 KV 缓存。在高请求量下，系统提示的缓存命中率达到 30–50%，直接转化为预填充算力的节省。

**推测解码**：对于延迟敏感的场景（交互式对话、语音），字节跳动采用推测解码来降低首 token 时延（TTFT）和 token 间延迟。草稿模型每步提出多个 token，目标模型并行验证。在 batch size 为 1 时，对于较短的可预测输出，这可以将吞吐量提升 2–3 倍。

### 多区域部署与监管约束

字节跳动同时服务两个监管要求截然不同的地理市场：

**豆包（中国）**：从中国数据中心提供服务，受中国 AI 内容法规约束，需要设备端或服务端内容审核。模型须通过国家互联网信息办公室（网信办）的算法备案要求。

**国际产品（TikTok 集成）**：从中国以外的基础设施提供服务，以满足欧盟、美国及东南亚的数据本地化要求。"德州计划"（美国 TikTok 数据存储于甲骨文基础设施）代表了字节跳动用来分离中外服务路径的合规架构。

多区域要求带来了额外的工程开销：不同监管环境需要独立的模型检查点，独立的服务集群，在某些情况下还需要针对当地内容规范进行不同 RLHF 微调的模型变体。这是纯 API 服务商（如 Anthropic 和 OpenAI）在小得多的规模下才需要管理的部署复杂度。

## 硬件约束：H800 与 H100 的对比

出口管制制度对字节跳动的工程决策有实质影响：

**H800 与 H100 的规格对比**：H800 是 NVIDIA 面向出口管制设计的 H100 合规版本。关键差异如下：

| 规格 | H100 SXM5 | H800 SXM5 |
|---|---|---|
| BF16 Tensor Core TFLOPS | 989 | 989 |
| FP8 TFLOPS | 3,958 | 3,958 |
| HBM3 带宽 | 3.35 TB/s | 3.35 TB/s |
| NVLink 带宽 | 900 GB/s（双向） | 400 GB/s（双向） |
| NVSwitch 支持 | 是 | 是（缩减） |
| 节点间互联（IB） | 相同 | 相同 |

计算能力和显存带宽完全相同。约束在于 **NVLink 带宽**：400 GB/s 对比 900 GB/s。对于张量并行训练，节点内 AllReduce（TP 的主要集合通信操作）受 NVLink 带宽限制。以 TP=8 为例，每次前向和反向传播都需要通过 NVLink 传输 1/8 的激活张量。NVLink 带宽减少 55%，意味着 TP 通信成为瓶颈的临界点发生了偏移。实践后果是：字节跳动在 H800 上的训练配置要么采用更大的流水线并行度（每节点参数量更少，单节点 AllReduce 数据量更小），要么采用更大的微批次（用更多计算量来摊薄 NVLink 延迟）。

MegaScale 的分层 AllReduce——节点内 NVLink，节点间 IB——正是针对这一约束设计的。通过最小化节点内 NVLink 传输的数据量，该架构在 NVLink 带宽不足的情况下，吞吐量损失也不会与带宽损失成正比。

字节跳动也已开始评估**华为昇腾 910B** 用于训练负载。昇腾 910B 提供有竞争力的算力（每芯片 256 TFLOPS BF16），通过 HiCCS（华为的 NVLink 同类产品）提供合理的互联带宽，但缺乏成熟的 CUDA 软件生态。将训练和推理栈迁移到昇腾，要么需要框架层面的抽象（使用华为的 CUDA 类比工具 CANN），要么需要针对特定硬件重写算子。这一迁移压力是中国 AI 实验室特有的重大工程投入。
