# Computer Use（计算机操控）

- **作者 / 机构**：Anthropic
- **发布时间**：2024 年 10 月（公开测试版，随 claude-3-5-sonnet-20241022 发布）
- **链接**：[Anthropic 博客](https://www.anthropic.com/news/developing-computer-use) · [API 文档](https://docs.anthropic.com/en/docs/build-with-claude/computer-use) · [参考实现](https://github.com/anthropic/anthropic-quickstarts/tree/main/computer-use-demo)

## 概述

Computer Use 是 Anthropic 在 API 层面提供的一项功能，它赋予 Claude 对真实桌面或浏览器环境的**基于截图的动作空间**。模型接收一张像素渲染的截图，推断当前界面状态，选择一个动作（点击、输入、滚动、按键），执行该动作，再接收下一张截图，如此循环。整个过程没有 DOM 访问，没有可访问性树，没有任何结构化的页面表示——只有像素级别的感知。这种普适性既是 Computer Use 的核心能力，也是其工程成本的根源：每一步都需要完整的视觉模型推理调用，延迟和 token 预算因此成为所有生产部署的首要约束。

## 背景与动机

浏览器自动化已存在数十年，但所有先前方案都要求对被控应用具有结构化访问权限：

- **Playwright / Puppeteer / Selenium**——程序化 DOM 操作，需要可控浏览器和结构化选择器；
- **RPA 工具（UiPath、Automation Anywhere）**——坐标录制点击，对 UI 变更脆弱，需要显式脚本编写；
- **浏览器扩展**——向页面注入 JavaScript，仅限 Web 层，无法控制原生桌面应用；
- **可访问性 API（Windows UIAutomation、macOS AXUIElement）**——暴露语义元素树，但各应用实现参差不齐，经常不完整。

所有结构化方案都在同一类场景下失效：遗留桌面应用、PDF 查看器、视频流、游戏、不提供任何编程 API 的第三方 SaaS 工具。Computer Use 的纯像素界面可以处理所有这些场景，因为它对应用本身没有任何要求。模型的任务与人类完全相同：看屏幕，决定要做什么，移动光标，按下按键。

这项能力随着大型视觉语言模型（VLM）的成熟而成为现实。使 Claude 3.5 Sonnet 能准确描述图像的同一架构进步，也使其能够将文本意图映射到截图中的像素坐标——模型在单次前向传播中隐式地完成版面解析、OCR 和空间推理。

## 动作空间

`computer_use` 工具以标准 Claude API 工具使用格式声明。当其被包含在请求中时，模型可以在响应中以工具调用的形式触发它。该工具有一个 `action` 字段用于分发，支持以下八种子动作：

```
screenshot                        → 捕获当前屏幕状态（返回 base64 PNG）
left_click(coordinate: [x, y])    → 在绝对像素坐标处左键单击
right_click(coordinate: [x, y])   → 右键单击（弹出上下文菜单）
double_click(coordinate: [x, y])  → 双击（打开 / 激活元素）
mouse_move(coordinate: [x, y])    → 鼠标移动但不点击（用于工具提示、悬浮菜单）
type(text: str)                   → 在当前光标位置键入文本
key(text: str)                    → 按键或组合键，如 "ctrl+c"、"Return"、"Tab"
scroll(coordinate: [x, y],
       direction: "up"|"down"|"left"|"right",
       amount: int)               → 鼠标滚轮事件
```

坐标是**截图分辨率下的绝对像素**。模型必须从返回的截图中视觉推断这些坐标——它没有元素位置的真值数据，没有边界框元数据，也没有悬浮事件。这正是视觉定位最困难的核心原因。

动作循环始终是：

1. 调用 `screenshot` 获取当前状态；
2. 推理下一步应当做什么（规划 + 视觉定位目标）；
3. 发出点击 / 输入 / 滚动 / 按键动作；
4. 返回第 1 步。

模型无法原子性地批量执行多个动作。每个动作都发送给宿主，执行后下一张截图才会反映结果。这种顺序结构意味着每个规划错误在下一步恰好可见并可被纠正——但也意味着 N 步任务需要 N 次往返。

## 视觉定位

视觉定位是将语义意图（"点击提交按钮"）转化为绝对像素坐标的过程。它需要：

1. **文本识别（OCR）**——在截图中找到文字"提交"；
2. **空间版面解析**——确定包含该文字的按钮的边界框；
3. **质心估算**——在边界框的中心或附近选取点击目标。

Claude 通过其视觉编码器隐式完成所有这些工作（ViT 风格的 patch tokenizer 后接交叉注意力与语言模型主干——参见 [VLM 服务](../../multimodal/vlm-serving/)）。模型在工具调用中直接输出 `coordinate: [x, y]`，没有任何中间边界框标注。当模型出错时，要么是元素识别错误（点了错误的按钮），要么是质心估算偏差（点在目标旁边而非目标上）。两种失败模式在下一步都可纠正，前提是模型观察到什么都没发生或发生了错误的事情。

根据经验，准确率在以下情况下明显下降：

- **密集 UI**——许多小型、紧密排列的元素（电子表格单元格、带侧边栏控件的代码编辑器）；
- **非标准视觉语言**——使用自定义 widget 工具包的遗留应用（Qt、Java Swing、旧版 Win32），其外观与典型 Web UI 差异显著；
- **低分辨率下的小字**——在 720p 截图中以 9–11pt 渲染的字体只有几个像素宽，OCR 准确率急剧下降；
- **动态内容**——加载动画、截图之间的过渡动效意味着截图 N 中的 UI 已不是模型在截图 N-1 中规划时的状态。

更高分辨率的截图可以提升小元素的准确率，但直接增加编码成本。Anthropic 的建议是在发送前将截图缩放到 **1366 × 768** 以内——这一设置在实验上对大多数桌面和浏览器 UI 实现了准确率与 token 成本的最优平衡。

## 延迟分析

单次 Computer Use 步骤的延迟构成如下：

```
step_latency = t_screenshot + t_encode + t_llm + t_execute

其中：
  t_screenshot ≈ 50–150 ms    （X11 帧缓冲捕获或无头浏览器截图）
  t_encode     ≈ 10–30 ms     （JPEG/PNG 压缩 + base64，CPU 执行）
  t_llm        ≈ 2,000–5,000 ms  （claude-3-5-sonnet 视觉推理，含网络往返）
  t_execute    ≈ 100–500 ms   （xdotool 点击/输入，Playwright 动作，或类似工具）

典型总计：2.5 – 6 秒 / 步
```

对于 10 步任务，这意味着 **25–60 秒的实际耗时**。完成相同任务的人类通常需要 5–15 秒。3–10 倍的差距几乎完全来自 LLM 推理时间——其他环节均在亚秒级。这对任务设计的启示是：Computer Use 适合**准确性优先于延迟**的场景：从遗留应用抓取数据、夜间批量填表工作流、与没有 API 的软件集成。它不适合需要亚秒级响应时间的交互式工作流。

视觉模型的 TTFT（首 token 延迟）也高于纯文本模型，因为视觉编码器必须在自回归生成开始前完成图像处理。在 1280 × 800 分辨率下，Claude 视觉调用的 TTFT 比相同输出 token 数量的纯文本调用高约 20–40%。

## Token 成本

Claude 的视觉编码将截图切分为固定大小的 patch。1280 × 800 的图像在标准切块分辨率下消耗约 **1,600–2,000 个输入 token**。精确数量取决于切块粒度和图像是灰度还是彩色。

对于 20 步轨迹，仅图像部分的成本即为：

```
20 张截图 × 1,800 token / 截图 = 36,000 tokens
```

加上系统提示（约 500 token）、任务描述（约 200 token）以及逐渐增长的文本对话（约 50 token/步 × 20 步 = 1,000 token），一个 20 步任务的总上下文约为 **38,000–42,000 token**。按 Claude 3.5 Sonnet 的定价，仅输入 token 每个任务约需 $0.12–$0.15。

关键的缓解手段是**前缀缓存**（参见 [../building-effective-agents/](../building-effective-agents/)）。截图在轨迹中以长前缀的形式累积。如果编排器在接收到每张截图时立即将其固定到缓存中，后续步骤只需为新截图和新文本计算注意力，而无需重新编码所有之前的截图。对于长轨迹，这可将每步成本降低 50–70%。系统提示和静态任务指令应始终置于缓存前缀中。

对于高频部署（每天数百个任务），成本优化通常包括：

- 降低截图频率——仅在规划步骤前立即截图，而不是每次动作后都截图；
- 大幅降低截图分辨率——1024 × 640 对于典型 Web UI 通常已经足够；
- 对系统提示和长期任务上下文使用前缀缓存；
- 一旦检测到成功即立即终止会话，而不是让模型再截一张确认截图。

## 部署基础设施

生产级 Computer Use 部署需要以下组件：

**虚拟显示层**：用于渲染屏幕的无头环境。在 Linux 上，`Xvfb`（X 虚拟帧缓冲）提供虚拟 X11 显示。对于仅限浏览器的任务，无头 Chromium 实例（通过 Playwright）即可满足需求。对于完整桌面任务，标准做法是在 Xvfb 之上运行轻量级窗口管理器（Openbox、Fluxbox）。

**截图捕获**：`scrot`、`import`（ImageMagick）或 Playwright 的 `page.screenshot()`。延迟应低于 100ms；在现代服务器上使用 Xvfb + scrot，50–80ms 是典型水平。

**动作执行**：`xdotool` 用于 X11 上的键鼠操作；Playwright 的 action API 用于浏览器原生任务。xdotool 增加约 20ms 执行开销；Playwright 的浏览器端动作通常更快。

**会话状态管理**：模型除截图可见内容外无法内省自身的动作历史。编排器必须维护会话状态：任务描述、步骤计数、已执行动作历史、成功标准、超时限制。在遇到意外状态（例如模型未预料到的对话框）时，编排器应检测异常，并注入纠正上下文或触发重试。

**容器隔离**：所有这些组件都运行在专用 Docker 容器中，除目标应用外无网络访问。容器在每个任务完成后被销毁。这不是可选项——Computer Use 可以执行任意键盘和鼠标动作，包括打开终端、运行 shell 命令和退出目标应用程序。没有隔离，故障或被对抗性提示操控的模型可能对宿主系统造成严重破坏。

**重试逻辑**：任务级重试限制（例如最多 3 次）和每步看门狗计时器（例如每步 30 秒）可防止无限循环。当某步没有在 UI 中产生任何可见变化时，编排器可以提示模型重新考虑，或终止并重试。

## 安全注意事项

从操作安全角度来看，Computer Use 是 Claude 风险最高的能力之一。模型可以：

- 打开终端并执行 shell 命令；
- 浏览任意 URL（泄露屏幕上可见的敏感数据）；
- 通过应用 UI 删除文件；
- 提交表单、发起购买、发送电子邮件。

Anthropic 对部署的安全指导：

1. **最低权限容器**：除目标服务外无网络访问；无宿主文件系统写挂载；不转发宿主凭证；
2. **人工审核检查点**：对于高风险动作（确认购买、发送邮件、删除文件），代理工作流应暂停并要求明确的人工批准后再继续；
3. **提示注入防范**：攻击者可以在屏幕上植入文本（例如在被浏览的网页中），指示模型执行非预期动作；系统提示应明确告知模型忽略与原始任务不符的屏幕上的指令；
4. **系统提示中的范围限制**：指示模型拒绝超出任务范围的动作（例如："您正在填写一份费用报告；不要导航到任何其他页面"）；
5. **破坏性动作速率限制**：动作执行与 xdotool/Playwright 之间的策略层可拒绝匹配破坏性模式的动作——例如向终端发送 `rm -rf` 的任何键盘序列。

## 方案对比

| 方案 | 准确率 | 部署复杂度 | 普适性 | 每动作延迟 | 成本 |
|---|---|---|---|---|---|
| Computer Use（视觉方案） | 中–高 | 低（容器化 + API） | 通用——任意 UI | 3–6 秒（LLM 调用） | 高（视觉 token） |
| Playwright DOM 自动化 | 极高 | 中（需维护选择器） | 仅限 Web | 10–100 ms | 低 |
| 浏览器扩展（JS 注入） | 高 | 中 | 仅限 Web，无原生支持 | 10–50 ms | 低 |
| RPA（UiPath / Automation Anywhere） | 中 | 高（需录制坐标） | 桌面 + Web | 100–500 ms | 中（授权费） |
| 可访问性 API（UIAutomation） | 高 | 高（特定于应用） | 仅限原生应用 | 50–200 ms | 低 |
| MCP 浏览器工具 | 高 | 低（协议层） | 仅限 Web | 50–500 ms | 低 |

实践中的决策规则：如果目标是具有稳定 DOM 的现代 Web 应用，使用 Playwright。如果目标是没有编程接口的遗留或第三方应用，使用 Computer Use。如果同一工作流中两者都有，Computer Use 提供统一接口，代价是延迟和每步 LLM 推理预算。

## 与代理模式的关系

Computer Use 是 [../building-effective-agents/](../building-effective-agents/) 中"增强型 LLM"模式发展到极致的产物：LLM 的工具不是结构化 API 调用，而是原始 UI 原语。代理循环是相同的感知-推理-行动周期，但感知是像素数组，行动是鼠标坐标。

这意味着所有代理循环工程考量都以更高强度适用：

- **上下文窗口管理**至关重要，因为截图是大量 token，会快速累积；
- **错误恢复**必须健壮，因为 UI 状态比结构化 API 响应更多变；
- **并行化**受限——步骤本质上是顺序的（不能同时点击两处），但多个独立任务会话可以跨容器并行运行。

跨越多个不同应用上下文的 Computer Use 任务（例如，从应用 A 复制数据，粘贴到应用 B，保存到应用 C）最好建模为多代理工作流：每个子代理负责单一应用范围，父编排器在它们之间传递状态——这样可以减少每个代理的上下文窗口，并限制故障域。

MCP（参见 [../mcp/](../mcp/)）可以将 Computer Use 动作作为 MCP 工具暴露出来，允许更大的代理系统将 UI 控制委托给 Computer Use 子进程服务器。当一个更大的代理系统需要 UI 交互作为众多能力之一，又不想将视觉模型基础设施与主编排层耦合时，这种方式非常有用。
