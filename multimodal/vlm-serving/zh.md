# VLM 服务——生产级视觉语言模型基础设施

- **作者 / 机构**：综合词条——综合自 vLLM 多模态支持、LLaVA-NeXT、Llama 4、Qwen-VL 服务及生产部署实践
- **发表时间**：2024 年（持续更新）
- **链接**：[vLLM 多模态文档](https://docs.vllm.ai/en/latest/models/vlm.html) · [LLaVA-NeXT](https://llava-vl.github.io/blog/2024-01-30-llava-next/) · [Qwen-VL](https://arxiv.org/abs/2308.12966) · [Llama 4](https://ai.meta.com/blog/llama-4-multimodal-intelligence/)

## 一句话总结

在生产环境中服务视觉语言模型，需要重新审视纯文本 LLM 服务的每一个假设。单张 1024×1024 图像经 336px 分块处理后产生 2304 个视觉 token——是典型文本提示的 10–50 倍——彻底颠覆了预填充/解码的平衡，并对批处理调度器造成严峻压力。核心基础设施变更包括：将视觉编码器作为独立预处理步骤运行，基于图像内容哈希实现重复图像的前缀缓存，使用分块预填充防止视觉密集型请求独占 GPU，以及通过序列打包（而非填充）处理异构序列组合（每个请求包含 0 到多张图像）。

## 背景与动机

纯文本 LLM 服务的特征已十分清晰：预填充处理输入提示词（数百 token，速度快），解码逐 token 生成输出（慢，受内存带宽限制）。vLLM、PagedAttention 和持续批处理都针对这一配置进行了优化。VLM 打破了这一模型：

- **预填充主导**：单张 LLaVA-NeXT 图像（4 块，336px）在任何文本之前贡献 2304 个视觉 token。对于 50 字的问题，视觉 token 是文本的 46 倍。
- **异构请求**：某些请求无图像，某些有 1 张，某些有 4 张。批次组成剧烈变化。
- **视觉编码器不是 LLM**：视觉编码器（通常是 CLIP ViT-L/14）作为独立模型运行，可能在不同硬件上，必须独立调度。
- **图像 KV 缓存**：视觉 token 可按图像内容在请求间缓存，而文本几乎不重复。

本词条综合了解决上述挑战的生产模式，来源于 [LLaVA](../llava/zh.md)、[Llama 4](../../meta/llama4/zh.md)、[Qwen3](../../qwen/qwen3/zh.md) 以及 vLLM 和 SGLang 服务栈。

## 视觉 Token 预填充经济学

### 各配置的 Token 数量

| 模型 / 配置 | 图像尺寸 | 分块数 | Token/块 | 视觉 token | 文本 token（典型） | 比值 |
|---|---|---|---|---|---|---|
| LLaVA-1.5 | 336×336 | 1 | 576 | 576 | 50 | 11.5× |
| LLaVA-NeXT 2×2 | 1024×1024 | 4+1 | 576 | 2880 | 50 | 57.6× |
| Qwen-VL 448px | 448×448 | 1 | 1024 | 1024 | 50 | 20.5× |
| Llama 4 Scout | 336px 动态 | 最多 16 | 256 | ~4096 | 50 | 82× |
| 多图（4 张） | 各 336px | 4 | 576 | 2304 | 100 | 23× |

在这些比值下，标准预填充调度逻辑被彻底改变。单张 4 块图像请求的预填充耗时相当于生成约 2880 个输出 token——实际上会阻塞批次中所有其他请求的解码吞吐量。

### 预填充成本 vs. 解码成本

对于一个 2880 个视觉 token 加 100 个文本 token 的 LLaVA-NeXT 请求：

- 预填充：2980 个 token × LLM 前向传播（一次，完全并行）→ 在 A100 上约 500ms（7B 模型）。
- 解码：200 个输出 token × 200 次 LLM 前向传播（顺序）→ 约 400ms。

预填充占主导。在纯文本服务中，预填充很少超过解码；在 VLM 服务中，它通常超过。

## 可变分辨率分块策略

### 固定 vs. 动态分块数

**固定分块**（LLaVA-NeXT 原版）：无论纵横比如何，始终使用 2×2 网格。实现简单；对非方形图像浪费分块（竖向照片会在一个维度上填充）。

**动态分块**（LLaVA-NeXT 动态版、Qwen-VL、Llama 4）：选择在最小填充下最好保持纵横比的分块网格：

```
对于 W×H 的输入图像，目标 tile 尺寸 T×T：
- 枚举网格选项：1×1、1×2、2×1、1×3、3×1、2×2
- 对每个网格 (n_w, n_h)：将图像缩放以适应 n_w×T × n_h×T（带填充）
- 选择填充最少的网格
- 始终附加降采样的全局缩略图
```

与固定 2×2 相比，动态分块将真实世界图像分布的平均 token 数减少 15–30%。基础设施含义：**在构建批次时，每个请求的 token 数量是可变且不可预测的**。

### 纵横比保留

将图像填充到固定分辨率会在均匀灰色边框上浪费 token。保持纵横比的分块确保，例如，640×480 图像使用 2×2 网格（960×720 边界框），而不是被拉伸为 672×672。服务系统必须处理每个请求可变的 N——这直接使注意力批处理复杂化。

## 图像 KV 缓存——图像前缀缓存

### 优化机会

若同一图像出现在多个请求中（FAQ 机器人回答关于同一产品图像的问题、批量处理固定文档集），视觉 token 在请求间完全相同。若视觉 token 始终位于序列开头，它们构成**可缓存的前缀**。

[前缀缓存](../../foundational/prefix-caching/zh.md)通过哈希 token 序列来工作，当前缀匹配时复用 KV 缓存块。对于视觉 token，哈希基于图像内容（或像素值及编码配置的确定性哈希）计算。缓存命中 → 完全跳过这些 token 的预填充，复用存储的 K 和 V 张量。

### 缓存键设计

```
image_cache_key = sha256(
    image_bytes +
    encoder_config_hash +   # ViT 模型版本、分辨率
    projector_config_hash   # MLP 权重版本
)
```

此键对于相同图像和模型版本的请求是稳定的。缓存命中时，576 或 2880 个 K/V 块从 KV 缓存池中取出，无需对这些位置重新运行 LLM 预填充。

### 缓存命中的经济价值

对于 7B 模型，576 个缓存视觉 token（FP16，32 层，32 个 KV 头，d_k=128）：
- KV 大小 = 576 × 32 × 2 × 128 × 2 字节 = **每张图像 9.4 MB**
- 每次命中节省的预填充计算 ≈ 500ms × (576/2980) ≈ 96ms

对于针对同一图像运行 10 次查询的文档处理流水线：缓存节省 9 × 96ms = 864ms 计算，代价是 9.4 MB KV 缓存存储。以 GPU 小时成本计算，缓存命中对高复用工作负载具有相当可观的价值。

## 编码器-解码器服务模式

### 模式 1：独立编码器步骤（标准 LLaVA）

```
请求携带图像+文本到达
  → 步骤 1：将图像路由至视觉编码器（CLIP ViT-L/14）
            输出：576 个视觉特征向量（独立 GPU 或同一 GPU 提前运行）
  → 步骤 2：通过投影器 MLP
            输出：576 个 LLM 空间 token 嵌入
  → 步骤 3：拼接 [视觉 token] + [文本 token]
            输入 LLM 预填充
  → 步骤 4：LLM 预填充 + 解码（标准）
```

步骤 1–2 在批次中的图像间完全可并行。视觉编码器可与 LLM 在不同 CUDA 流甚至独立 GPU 上批量处理。在高吞吐量服务中，专用视觉编码器工作进程预处理图像并缓存投影嵌入。

### 模式 2：原生多模态注意力（Llama 4 / MM-DiT）

部分架构（Llama 4 Scout/Maverick、Flamingo、BLIP-2）以不同方式集成视觉 token：

- 交叉注意力层：视觉特征保存在侧边缓冲区；语言 token 通过独立交叉注意力头关注它们。视觉编码器输出保持其原始维度（不投影到 LLM 维度）。
- 交错 token：图像 token 在图像位置直接插入文本 token 流中。

对于 [Llama 4](../../meta/llama4/zh.md)，原生多模态注意力层在特定层中对视觉和文本 token 进行联合处理，比瓶颈投影器能实现更深层的视觉-语言融合。服务更为复杂：视觉编码器必须与 LLM 协同调度，其输出不能简单地前置于序列。

## 异构序列批处理

### 填充问题

朴素的批处理方式将批次中所有序列填充到相同长度：

- 请求 A：2880 个视觉 + 50 个文本 = 2930 个 token
- 请求 B：0 个视觉 + 100 个文本 = 100 个 token

将 B 填充到 2930 个 token 浪费了 B 的 96.6% 计算。批量大小为 8 的混合视觉/文本请求中，平均浪费可达 60–80%。

### 序列打包

序列打包（也称"多包"或"拼接批次"）将多个序列拼接成一个张量，通过注意力掩码防止跨序列注意力：

```
[序列 A token (2930)] [分隔] [序列 B token (100)] [分隔] [序列 C token (400)] ...
```

所有序列打包到单一张量中，注意力掩码为块对角形式。每个序列只关注自身 token。这消除了填充浪费，是 vLLM 持续批处理处理混合请求的方案。

实现需要仔细处理位置嵌入（每个序列重置）和注意力掩码（块对角）。对于视觉 token，位置嵌入约定必须保持一致：大多数系统在打包批次内每个序列开头将位置重置为 0。

### [PagedAttention](../../foundational/paged-attention/zh.md) 与视觉 Token

vLLM 的 PagedAttention 以固定大小页面分配 KV 缓存。视觉 token 与其他预填充 token 一样分配页面。关键区别：若同一图像已在 KV 缓存中，视觉 token 页面可在请求间**共享**——同一物理页面被映射到多个虚拟 KV 缓存中。这与 PagedAttention 在请求间共享系统提示词 KV 缓存的逻辑完全相同。

## 视觉 Token 的分块预填充

单次前向传播中 2880 个 token 的视觉预填充在 A100 上约需 500ms——期间持续批次中所有其他请求均被阻塞。[分块预填充](../../foundational/chunked-prefill/zh.md)将 2880 个 token 切分为例如 512 个 token 的块：

- 块 1：预填充 token 0–511（视觉 token 0–511）
- 块 2：预填充 token 512–1023（视觉 token 512–1023）
- ...
- 块 6：预填充 token 2560–2879（视觉 token 2560–2879）+ 文本问题
- 解码阶段开始

块与块之间，调度器可注入其他请求的解码步骤，即使大型 VLM 预填充正在进行，也能维持纯文本请求的尾部延迟。代价：更多调度开销，某些实现中块间 KV 缓存不复用导致总计算量略微增加。

## 工程 Tradeoff

| 决策 | 得到什么 | 放弃什么 |
|---|---|---|
| 独立视觉编码器步骤 | 编码器可独立批处理/流水线；视觉嵌入可缓存 | 双模型调度复杂度；编码器和 LLM 必须版本协同 |
| 图像前缀缓存 | 消除重复图像的冗余预填充；FAQ/文档工作负载大幅收益 | 缓存内存开销（每图约 10 MB）；模型更新时缓存失效 |
| 动态分块 | 非方形图像 token 数减少；每 token 质量更高 | 可变 token 数使批次构建复杂；调度器须动态重排 |
| 序列打包 | 接近零的填充浪费；更高 GPU 利用率 | 复杂的注意力掩码；需要位置嵌入重置逻辑 |
| 分块预填充 | 防止视觉预填充独占 GPU；文本请求 P99 延迟降低 | 总计算量略微增加；调度器复杂度上升；块间需要状态管理 |
| 原生交叉注意力（Llama 4） | 更深的视觉-语言融合；模型质量提升 | 更复杂的服务计算图；视觉特征必须与 LLM 协同调度；难以缓存 |

## 实验与结果

来自 vLLM VLM 基准测试和生产测量：

- **不打包的吞吐量**：批量大小 16 的混合模态批次（50% 图像请求）因填充浪费 GPU 利用率约 40%。
- **序列打包后的吞吐量**：相同工作负载 → GPU 利用率约 75%，吞吐量提升约 1.9×。
- **图像前缀缓存**：FAQ 工作负载（每张独立图像 10 个问题），缓存预热后均值 TTFT（首 token 时间）降低 45–60%。
- **分块预填充**：混合批次中纯文本请求的 P99 TTFT 从约 4s（被图像预填充阻塞）降至块大小 512 时的约 0.8s。

## 个人评注

VLM 服务暴露了 LLM 服务栈中纯文本部署从未触及的根本性张力：对于视觉输入，预填充和解码阶段的成本如此不对称，以至于整个调度逻辑必须重新考虑。持续批处理范式——请求到达即处理，交错预填充和解码——是为文本设计的，此时预填充量较小。当单张图像注入 2880 个预填充 token 时，不带分块的持续批处理实际上退化为串行处理。

当前开源服务栈中，图像前缀缓存的机会被低估了。对于任何用户反复询问同一图像的应用（电商产品问答、文档分析、视频帧分析），缓存视觉 KV 张量可将热门图像的预填充计算减少 80% 以上。这需要将图像视为调度器中的一等缓存键——是[前缀缓存](../../foundational/prefix-caching/zh.md)的直接扩展，但需要将图像内容哈希连接到请求预处理流水线中。

长期趋势指向可学习视觉 token 压缩：用小型重采样器（Q-Former、Perceiver Resampler 或 token 合并）将 576 个 token 压缩到 64–128 个，且准确率损失可接受。这种压缩已出现在 BLIP-2、InstructBLIP 和 [Llama 4](../../meta/llama4/zh.md) 的交叉注意力层中。每图 64 个 token 时，整个 VLM 服务问题大幅简化：视觉预填充变得可忽略，缓存变得不那么关键，批次异构性也可管理。目前这种压缩的准确率成本在标准基准上为 2–5%，但随着重采样器架构的成熟，差距正在迅速缩小。
