# 分块预填充 — Sarathi-Serve

- **作者 / 机构**：Amey Agrawal、Nitin Kedia 等（微软亚洲研究院 / 印度科学研究院班加罗尔分校）
- **发表时间**：2024-03
- **链接**：[arXiv:2403.02310](https://arxiv.org/abs/2403.02310) · [代码](https://github.com/microsoft/sarathi-serve) · [vLLM 集成文档](https://docs.vllm.ai/en/latest/models/chunked_prefill.html)

## TL;DR

分块预填充（chunked prefill）将长提示词切分为固定大小的块，并在单个批次内与解码步骤交叉执行。这彻底消除了标准连续批处理中令人头痛的预填充–解码干扰问题：长预填充不再独占 GPU 并阻塞所有并发解码 token。在长短提示词混合的工作负载下，Sarathi-Serve 相比 vLLM 的连续批处理将 P99 首个 token 时延（TTFT）降低了最高 6.8×，同时解码吞吐量保持在基线的 98%。该技术此后已合并进入 vLLM（v0.4.0）和 SGLang，成为超越朴素 Orca 风格服务的事实标准调度升级方案。

## 背景与动机

### Orca 基线及其剩余瓶颈

Orca（Yu 等，OSDI 2022）为 LLM 服务引入了连续批处理：服务端不再等待整个批次完成后才启动下一批，而是在迭代层面处理请求，每次前向传播时动态插入和逐出请求。这消除了静态批处理中的填充浪费，显著提升了 GPU 利用率。

但 Orca 留下了一个未解问题：**预填充–解码干扰**。在 LLM 推理中，每个新请求都会经历预填充阶段——并行处理整个提示词以填充 KV 缓存——然后进入解码阶段，每次生成一个 token。这两个阶段在计算特性上存在根本差异：

- **预填充是计算密集型**：整个提示词在一次（或几次）前向传播中并行处理，产生大规模矩阵乘法，可以充分饱和张量核心。单个 8K token 的提示词，根据模型大小和硬件的不同，可能需要 50–200 ms。
- **解码是内存带宽密集型**：每次解码步骤每个请求只处理一个 token，产生极小的矩阵乘法，但需要读取该请求的整个 KV 缓存。GPU 计算利用率通常较低，瓶颈在于内存带宽。

当连续批处理服务器将预填充和解码混在同一次前向传播中时，**预填充会挤占解码**。进入批次的长预填充请求会迫使批次中所有其他解码请求等待整个预填充的时间才能获得下一个 token。在此期间，解码请求毫无进展。

### 两种失效模式

**短请求的高 TTFT。** 用户提交一个 50 token 的提示词，排在一个有 10K token 提示词的请求后面，即便他们自己的提示词单独处理只需几毫秒，也要等待数百毫秒才能获得第一个 token。在突发流量下，P99 TTFT 会膨胀到秒级。

**解码吞吐量下降。** 预填充阶段会占用解码也需要的计算单元。即便混在同一批次中，计算密集的预填充阶段也会让内存带宽受限的解码得不到充分服务——在当前硬件上，两种操作无法清晰地流水线化。

### 替代方案

**DistServe / 预填充-解码分离**（Zhong 等，2024）通过将预填充请求路由到专用的预填充集群、将解码请求路由到单独的解码集群（通过 NVLink 或 InfiniBand 传输 KV 缓存）来解决这一问题。这种方式将两个阶段清晰分离，但至少需要 2× 的硬件资源，并引入了 KV 缓存网络传输的延迟。Mooncake（月之暗面，2024）将同样的思路应用于数据中心规模。

**Sarathi-Serve** 采用了不同的路径：通过永不发出完整预填充，在单张 GPU 上解决干扰问题。这种方式更经济、部署更简单，覆盖了大多数无法在经济上justify专用预填充集群的服务场景。

## 核心方法

### 分块预填充调度

核心思想很简单：

1. **将每个预填充切分为 C 个 token 的块**（块大小，可调超参数，通常为 256–1024）。
2. **每次前向传播是一个混合批次**：来自等待中预填充请求的一个或多个预填充块，加上所有活跃的解码 token。
3. **预填充请求每步推进 C 个 token**，完成其提示词处理。解码请求每步推进 1 个 token，与标准连续批处理相同。
4. **解码 token 永远不会被驱逐。** 每次前向传播都包含所有活跃的解码 token。任何解码请求都不会因等待预填充完成而停滞。

这创造了一种协作式调度：预填充请求与解码请求共享 GPU 时间，每次前向传播消耗 C 个 token 的预填充预算，而不是独占整个传播过程。长预填充被分散到多次前向传播中，而不是在一次大型突发中完成。

### 块大小控制权衡

参数 C 是主要调节旋钮：

- **小 C（如 128–256）：** 解码几乎不会停滞；排队的短请求 TTFT 接近理论最小值；预填充吞吐量有所降低，因为每次前向传播的预填充工作量较少，且每个块的调度开销相对更大。
- **大 C（如 2048–4096）：** 预填充吞吐量接近未分块时的性能；长预填充的第一个块仍然是较大的计算突发，可能使解码请求等待更长时间；当 C 等于完整提示词长度时，退化为朴素的连续批处理。

实践中，C = 512 是 Sarathi-Serve 的默认值，也是大多数 vLLM 部署使用的值。它代表了典型工作负载分布下 TTFT–吞吐量 Pareto 曲线上的近最优点。

### KV 缓存管理与 PagedAttention 兼容性

一个关键的工程要求是分块预填充必须与 KV 缓存管理系统干净地集成。在 PagedAttention（Kwon 等，2023）中，KV 缓存被划分为固定大小的页面（通常每页 16–32 个 token）。预填充请求在处理其各块时逐步填充这些页面。

Sarathi-Serve 将块边界与页面边界对齐，以避免部分页面写入：如果页面大小为 P 个 token，块大小 C 应是 P 的倍数（或 C 的选取应使块不跨越页面边界）。这是调度层面的约束——不需要对 PagedAttention 内核进行任何修改。为预填充请求分配的 KV 缓存页面逐块填充，每个块完成后即可供注意力内核使用。

这清晰地分离了关注点：**分块预填充是调度层技术**，而非内核层技术。它与任何注意力内核（FlashAttention-2、FlashAttention-3、FlashInfer）和任何内存管理方案（PagedAttention、前缀缓存、SGLang 中的基数树）均兼容。

### 混合批次组成

带分块预填充的单次前向传播同时处理两种类型的 token：

- **预填充 token（来自一个或多个块）：** 使用标准因果掩码，对迄今为止累积的完整前缀做注意力计算。当前块中的所有 token 相互注意，并注意到该请求之前所有的 KV 缓存条目。
- **解码 token（每个活跃解码请求各一个）：** 对各自请求的完整 KV 缓存做注意力计算，与标准解码相同。

两种 token 类型的注意力计算有所不同：预填充 token 产生序列长度 × 序列长度的注意力模式；解码 token 产生 1 × 序列长度的注意力模式。FlashAttention 通过可变长度（varlen）批处理自然地处理这一情况——批次中各请求的查询、键、值张量沿请求维度拼接，并用累积序列长度索引数组指定边界。

**可达利用率（Attainable Utilization，AU）** 是 Sarathi-Serve 引入的核心指标：实际交付的吞吐量占硬件理论峰值速率下可达吞吐量的比例。在混合工作负载下，标准连续批处理的 AU 远低于 1.0，原因是预填充气泡——在大批次的计算密集型预填充阶段，GPU 处于空闲或低利用率状态。分块预填充通过在每次前向传播中保持解码和预填充工作的一致混合，避免了未分块调度的峰谷波动，从而提升了 AU。

### 与前缀缓存和基数树的交互

SGLang 的基数树缓存和 vLLM 的前缀缓存都会缓存共享提示词前缀的 KV 缓存条目。分块预填充与之优雅地交互：完全落在已缓存前缀内的块可以被跳过（KV 缓存条目已存在），调度器可以直接跳到第一个未缓存的块。这是纯粹的收益——分块预填充不会干扰前缀缓存。

## 工程权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| 分块预填充 vs 全长预填充 | 解码请求永不停滞；混合工作负载下 P99 TTFT 最高降低 6.8×；突发负载下延迟更可预测 | 每个请求的总预填充延迟略有增加（多次前向传播而非一次）；每次块切换有少量调度开销 |
| 小块大小 C（如 256） | 解码停滞近乎为零；排队的短请求 P99 尾延迟最优；token 间延迟最一致 | 有效预填充吞吐量降低；长提示词调度调用次数增多；上下文切换开销略有上升 |
| 大块大小 C（如 2048） | 每次前向传播的预填充吞吐量接近最大值；长提示词的调度决策次数减少 | 大块期间解码停滞风险重现；对于极端（超长）提示词，尾延迟趋近于未分块行为 |
| 分块预填充 vs 预填充-解码分离（DistServe / Mooncake） | 单 GPU 解决方案；无 KV 缓存网络传输开销；硬件成本更低；运维部署更简单 | 无法独立扩展预填充和解码资源；预填充和解码共享同一 GPU 的内存和计算预算；在极端预填充密集的工作负载下效果较弱 |
| 块-页面对齐（PagedAttention 集成） | 与 PagedAttention 干净集成；无需修改内核；与任何注意力实现兼容 | 块大小必须是页面大小的倍数；调度器须跟踪每个请求的块-页面偏移量；调度器数据结构状态增加 |

## 实验与结果

Sarathi-Serve 在两张 A100-80GB GPU（张量并行度为 2）上服务 LLaMA 2 70B，采用两种代表现实请求模式的工作负载分布进行评估：

**P99 TTFT 降低：** 在高请求速率下，将短（512 token）和长（8192 token）提示词混合的工作负载中，Sarathi-Serve 相比无分块的 vLLM 连续批处理实现了 **P99 TTFT 降低 6.8×**。P50 TTFT 改善更为温和（约 2–3×），反映出分块主要受益于排在长预填充后面的请求（尾部效应）。

**解码吞吐量保留：** 在 C = 512 时，解码 token 生成吞吐量（进行中请求的每秒 token 数）**保持在 vLLM 基线的 98%**。2% 的开销来自混合批次的额外调度开销，以及较小预填充块的轻微低效。

**可达利用率（AU）：** 峰值负载下，AU 从未分块连续批处理的约 0.55 提升到 Sarathi-Serve 的约 0.85——硬件使用效率提升 55%。与 1.0 之间的剩余差距反映了不可消除的调度开销和内存带宽受限的解码阶段。

**对块大小的敏感性：** TTFT–吞吐量 Pareto 曲线在 C = 256 到 C = 1024 之间呈现宽阔的平台区，意味着在此范围内系统对块大小的精确选取相对不敏感。默认的 C = 512 对大多数工作负载处于最优点附近。

**与预填充-解码分离的对比：** DistServe 以 2× 的硬件为代价实现了更低的绝对 TTFT。在中等请求速率下，Sarathi-Serve 使用与未分块 vLLM 相同的硬件，实现了与 DistServe 相当的 TTFT。在极高请求速率且提示词长度方差极大时，分离方案仍具优势。

## 复现说明

**Sarathi-Serve（原始实现）：**
- 代码仓库：`github.com/microsoft/sarathi-serve`
- 构建于 vLLM 之上；需要 CUDA 11.8+、Python 3.9+
- 块大小 C 通过 `--sarathi-chunk-size` 参数控制
- 支持 LLaMA、Mistral、Mixtral 及任何 vLLM 兼容架构

**vLLM 集成（v0.4.0+）：**
```bash
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-2-70b-hf \
    --enable-chunked-prefill \
    --max-num-batched-tokens 2048
```
`--max-num-batched-tokens` 参数控制每次前向传播的有效 token 预算。设为 512–1024 可近似还原 Sarathi-Serve 的默认行为。

**SGLang：** 对长上下文模型默认启用分块预填充，无需额外参数；块大小根据模型的上下文长度自动设定。

**关键调优旋钮：**
- `chunk_size`（C）：主要的延迟–吞吐量权衡旋钮。从 512 开始；若 P99 TTFT 是首要关注点，向 256 减小；若预填充吞吐量是优先项，向 1024 增大。
- `max_num_batched_tokens`：每次前向传播的总 token 预算（预填充块 + 解码 token）。应至少设为 `chunk_size + max_concurrent_decode_tokens`。

**工作负载注意事项：** 分块预填充在提示词长度方差大的工作负载下收益最显著。若所有请求的提示词长度相近（例如，输入固定为 4K token 的纯摘要 API），干扰问题相对较轻，分块带来的收益也较小。

## 评注

分块预填充是近年 LLM 服务研究中最简洁的系统设计胜利之一。洞察是简单的：预填充和解码之间的干扰来源于它们在不兼容的粒度上被调度——预填充独占整个前向传播，而解码希望分享每次前向传播。将预填充降至块粒度，就恢复了两者的对等性。

实现成本很低。分块预填充是调度器层面的变更，不需要新内核、新硬件或任何模型架构变动。块-页面对齐约束（用于 PagedAttention 兼容性）增加了少量调度复杂度，但这完全在生产推理系统的处理能力之内。

与预填充-解码分离（DistServe、Mooncake）的对比很有启发性。分离方案在功能上更强大——它允许独立扩展预填充和解码集群——但需要网络基础设施、KV 缓存传输协议和 2× 的硬件。对于无法负担专用预填充 GPU 的组织，Sarathi-Serve 以零额外硬件成本实现了大部分延迟收益。正确的选择取决于规模：在中小型服务负载下，Sarathi-Serve 几乎总是正确答案；在对 TTFT 有极端 SLA 要求的超大规模场景下，分离方案的开销才值得投入。

一个容易被忽视的方面：分块预填充还改善了跨请求优先级的**公平性**。没有分块时，排在长预填充后面的短请求会经历任意长的等待。有了分块预填充，每个请求每次前向传播都会有进展，最坏等待时间约为 `(完整提示词长度 / C)` 次前向传播——一个可预测、可控制的量。

该技术已被广泛采用：vLLM、SGLang 和 TensorRT-LLM 均已支持。对于任何使用连续批处理并处理可变长度提示词的服务栈，分块预填充现在是预期的基础配置。
