# 多租户 LoRA 推理服务 — SLoRA、Punica 与 CaraServe

- **作者 / 机构**：SLoRA：Sheng 等（UC Berkeley），arXiv:2311.03285，2023；Punica：Chen 等，arXiv:2310.18547，2023；CaraServe：2024
- **发表时间**：SLoRA：2023 年 11 月；Punica：2023 年 10 月；CaraServe：2024
- **链接**：[SLoRA](https://arxiv.org/abs/2311.03285) | [Punica](https://arxiv.org/abs/2310.18547)

## 一句话总结

在单个基础模型上服务数千个微调 LoRA 适配器是一个不同于单模型服务的基础设施问题。朴素方案——每个适配器一个 GPU 进程——因 GPU 利用率崩溃而无法扩展。SLoRA 通过按需在 CPU DRAM 和 GPU HBM 之间分页适配器权重解决这一问题，并将请求按适配器分组以最大化批处理效率。Punica 通过 SGMV 内核（分段聚集矩阵向量乘法）解决了正交的混合适配器批处理问题——一个自定义 CUDA 内核，能在单次内核启动中为多个不同适配器计算 ΔWx。两者共同定义了多租户 LoRA 服务的两个维度：内存高效的适配器管理和计算高效的混合批处理执行。

## 背景与动机

基于 LoRA 的微调（见 [../lora/zh.md](../lora/zh.md)）已成为 LLM 的主流适配方法：冻结基础模型，在每个注意力和 FFN 投影处插入低秩矩阵 ΔW = BA 进行训练。rank-16 的 70B 模型适配器大约增加 200–300 MB 权重；基础模型本身在 BF16 下为 140 GB。这种结构天然暗示了一个服务优化：**跨多个适配器共享基础模型**。

商业价值非常明显：一个服务 1000 个 Llama-3-70B 不同微调版本的平台，在朴素方案下每个适配器需要一台 GPU 服务器（140 GB）。通过适配器共享，只需要一个基础模型的 GPU 内存（140 GB），加上可以从 CPU DRAM 按需换入换出的适配器权重。

技术挑战：

1. **适配器内存管理**：1000 个适配器 × 200–300 MB = 200–300 GB 适配器权重。与基础模型同时放入 GPU HBM 根本不够。适配器必须存储在 CPU DRAM 中并按需加载。
2. **批处理效率**：如果每个请求使用不同的适配器，朴素批处理会串行化所有适配器计算——GPU 每次只处理一个适配器的 ΔW。对于批次中 k 个不同适配器，吞吐量降至单适配器基准的 1/k。
3. **冷启动延迟**：从 CPU DRAM 加载适配器到 GPU HBM 需要时间——PCIe 带宽约 32 GB/s，300 MB 适配器加载约需 10ms。

## LoRA 内存结构

在每个注意力和 FFN 层，LoRA 添加：

```
ΔW = B · A    其中 B ∈ R^{d×r}，A ∈ R^{r×k}
```

修改后的前向传播：

```
output = (W + ΔW) · x = W · x + B · (A · x)
```

`W · x` 是基础模型计算（所有适配器共享）。`B · (A · x)` 是适配器特定计算（每个适配器不同，O(r) 秩预算）。

对于 Llama-3-70B，在 80 层中对所有注意力投影（Q、K、V、O）和所有 FFN 投影（gate、up、down）应用 rank-16 LoRA：

```
适配器大小 ≈ 80 层 × 7 个投影 × 2 个矩阵 × rank × dim × 数据类型字节数
           ≈ 80 × 7 × 2 × 16 × 4096 × 2 字节（BF16）
           ≈ ~250 MB
```

rank 64 时，每个适配器约翻倍至 ~1 GB。秩的选择是适配器内存大小的主要调节旋钮。

## SLoRA：分页适配器加载

### 核心设计

SLoRA 将适配器权重类比于 PagedAttention（见 [../paged-attention/zh.md](../paged-attention/zh.md)）处理 KV 缓存的方式：一个必须在容量约束下管理的内存池，具有驱逐和按需加载功能。

**适配器内存池**：SLoRA 维护一个固定大小的 GPU 缓冲区用于适配器权重（例如，在基础模型占用 80 GB HBM 的服务器上，为适配器留 8 GB）。该缓冲区保存当前已加载的适配器。不使用时，适配器权重存储在 CPU DRAM 中。

**LRU 驱逐**：当需要新适配器且缓冲区已满时，驱逐最近最少使用的适配器（传回或直接丢弃）。驱逐策略与任何缓存系统相同——LRU 简单且在时间局部性下表现良好。

**PCIe 传输**：适配器加载使用带异步 DMA 传输的 CUDA 固定内存。通过 PCIe 4.0（32 GB/s）加载 250 MB 适配器约需 8ms。这是冷启动开销——某适配器的第一个请求承担此代价。后续对同一适配器的请求无需等待。

### 批处理策略：按适配器分组批次

SLoRA 的调度器按适配器分组请求：如果适配器 A 有 10 个待处理请求，适配器 B 有 5 个，SLoRA 在两个适配器都在 GPU 缓冲区时组成包含全部 15 个请求的批次，或在只加载了 A 时组成 A 的 10 个请求的批次。

这最大化了批次内 ΔW 计算的复用：共享适配器 A 的所有请求只需计算一次 `B_A · (A_A · x_batch)`，而非每请求各算一次。基础模型计算 `W · x_batch` 无论如何都已批处理。

权衡：按适配器分组批处理降低了批处理多样性。如果 15 个请求有很不同的输出长度，较短序列在等待较长序列完成时形成队头阻塞，降低 GPU 利用率。SLoRA 通过持续批处理部分缓解这一问题——短序列完成后在批次内被替换——但适配器局部性和序列长度多样性之间的根本矛盾仍然存在。

### 适配器调度

SLoRA 在基础推理调度器之上添加了适配器感知的调度层：

1. **热适配器检查**：请求到达时，检查其适配器是否已在 GPU HBM 中。
2. **预加载决策**：如果适配器不热，启动异步 PCIe 传输。请求在队列中等待，直到其适配器加载完毕。热适配器的请求立即调度。
3. **驱逐决策**：当缓冲区满且必须加载新适配器时，驱逐当前没有飞行中请求的 LRU 适配器。

系统维护适配器热度图——每个适配器请求到达率的滚动估计——以在请求到达前预加载适配器。这将高流量适配器的冷启动延迟从约 8ms 降至接近零。

## Punica：SGMV — 通过自定义 CUDA 内核实现混合适配器批处理

### 批处理问题

SLoRA 的按适配器分组方式回避了一个根本的效率问题：如果你*想*同时批处理来自不同适配器的请求怎么办？在具有 1000 个适配器、请求按泊松过程到达的多租户系统中，按适配器分组意味着某些适配器总是有薄批次（低吞吐量），某些积累大队列（高延迟）。

Punica 用不同方法解决这一问题：**允许任意混合适配器批次**，并通过单次内核调用高效计算异构适配器的 ΔW。

### SGMV：分段聚集矩阵向量乘法

关键洞察：在包含 N 个各使用不同适配器的请求的批次中，ΔW 贡献可以被计算为分段批量矩阵乘法。每个请求 `j` 使用适配器 `i_j`，带有矩阵 `B_{i_j}` 和 `A_{i_j}`。完整批次计算为：

```
对批次中每个请求 j：
    delta_output_j += B_{i_j} · (A_{i_j} · x_j)
```

这看起来像 N 个独立矩阵乘法，但 Punica 观察到，当适配器共享相同的秩 `r` 时，所有 `A` 矩阵形状均为 `r × k`，所有 `B` 矩阵形状均为 `d × r`。我们可以将所有 `A` 矩阵打包到 3D 张量 `A_stack[N, r, k]`，所有 `B` 矩阵打包到 `B_stack[N, d, r]`，然后用单个分段批量 GEMM 计算完整批次：

```
hidden = batched_mm(A_stack, x_batch)      # [N, r, 1] = [N, r, k] × [N, k, 1]
delta_output = batched_mm(B_stack, hidden)  # [N, d, 1] = [N, d, r] × [N, r, 1]
```

SGMV 内核直接在 CUDA 中用段偏移量实现这一点——名称中的"聚集"指从预填充的索引中为每个请求的适配器聚集正确的 `A` 和 `B` 矩阵。该内核将 N 次独立内核启动（每次有约 5–10 µs 的 CUDA 内核启动开销）替换为 1 次启动。

在批大小 32、32 个不同适配器的情况下，SGMV 比顺序单适配器 ΔW 计算快约 8 倍。批大小较小时优势减弱；批大小低于 4 时，由于 SGMV 的并行开销，逐请求内核启动可能更快。

### SGMV 的内存布局

Punica 将所有适配器的 `A` 和 `B` 矩阵同时保留在 GPU HBM 中——不将其分页到 CPU。这将并发服务的适配器数量限制为 HBM 容量 / (适配器大小 × 适配器池中的适配器数)。对于在 4× A100 80GB 上服务 rank-16 适配器（每个 250 MB）的 80B 模型：

```
可用于适配器的空间 ≈ (4 × 80 GB) - 基础模型 (140 GB) - KV 缓存 (~60 GB) = 120 GB
最大并发适配器数 ≈ 120 GB / 250 MB ≈ 480 个适配器
```

对于需要同时服务 480 个以上适配器的部署，Punica 的全 HBM 方法失效。SLoRA 的分页方式以冷启动延迟为代价处理这种情况。

## CaraServe：分页与混合批处理的结合

CaraServe（2024）综合了 SLoRA 和 Punica 的方法：

- 从 CPU DRAM 分页加载适配器（SLoRA 风格），处理超出 HBM 容量的适配器数量。
- SGMV 风格的混合适配器批处理，用于已在 HBM 中热加载的适配器。
- 调度器将"热"请求（适配器在 GPU HBM 中，可进行 SGMV 批处理）与"冷"请求（适配器在 CPU 上，必须等待 PCIe 传输）分开。

关键洞察是 SLoRA 和 Punica 解决的是正交问题：SLoRA 处理内存容量（适配器多于 GPU 可容纳数量），Punica 处理计算效率（异构适配器批处理）。CaraServe 同时处理两者。

## 工程权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| SLoRA 分页（适配器权重在 CPU DRAM） | 从单个基础模型服务无限数量的适配器；适配器数量不受 GPU HBM 限制 | PCIe 冷启动延迟（每次适配器加载约 8ms）；高驱逐率下 CPU DRAM 带宽争用 |
| 按适配器分组批处理（SLoRA） | 批次内最大 ΔW 复用；实现简单 | 批处理多样性降低；适配器组内的队头阻塞；低流量适配器批次薄 |
| SGMV 混合适配器批处理（Punica） | 真正的混合适配器批处理；异构适配器下接近基础模型吞吐量 | 所有活跃适配器必须同时在 GPU HBM 中；4× A100 80GB 上约 480 个适配器上限 |
| LRU 适配器驱逐 | 简单低开销的缓存策略；时间局部性下表现良好 | 适配器访问频率均匀的工作负载下表现差（所有适配器同等冷） |
| 低适配器秩（r=8 或 r=16） | 适配器内存占用小；PCIe 加载时间短 | 适配器表达能力受限；复杂任务适配可能需要更高的秩 |
| 适配器感知的持续批处理 | GPU 保持忙碌；短序列完成无需阻塞 | 需要跟踪每个飞行中请求的适配器状态；适配器数量增多时调度复杂性增加 |

## 实验与结果

**SLoRA**（论文结果）：
- 1000 个适配器，Llama-7B 基础模型，A100 40GB 服务器：与独立适配器进程的 vLLM 相比，吞吐量提升 4 倍；p99 延迟比带请求排队的单适配器服务改善 2 倍。
- 冷启动延迟：7–12ms 每适配器（PCIe 4.0 实测）；热服务延迟与基础模型服务相当。

**Punica**（论文结果）：
- A100 上批大小 32 的混合适配器批次：SGMV 与 SLoRA 风格的串行 ΔW 计算相比，吞吐量提升 2.5–4 倍。
- 批大小为 1 时，开销约为单适配器服务的 10%；批大小为 32 时，在相同硬件上接近单适配器吞吐量。

**CaraServe**（综合）：
- 在 8× A100 服务器上处理 2000+ 个适配器，p90 冷启动延迟 < 20ms。
- 稳态下吞吐量在单适配器最优值的 5% 以内。

## 评述

多租户 LoRA 服务问题是 ML 基础设施更广泛挑战的缩影：为研究场景构建的系统（一个模型、一张 GPU、最大化该模型的利用率）在运营现实是"多个模型、共享硬件、异构负载"时组合性差。SLoRA 和 Punica 各自从相邻系统工作中取了一个干净的抽象——vLLM 的分页内存管理、cuBLAS 的批量 GEMM——并精确地应用于 LoRA 服务场景。结果是一对系统，合在一起比任何单独一个都能更好地覆盖设计空间。

SGMV 内核值得特别关注，作为 ML 服务内核工程的案例研究。问题陈述——为批次中每个样本有不同 W 的情况计算 ΔWx——表面上需要 N 次内核启动。SGMV 将其重新表述为带聚集语义的分段批量 GEMM，将 N 次启动减少为 1 次。关键前提是所有适配器共享相同的秩 r，这在实践中几乎总是成立（秩是微调操作员设置的训练超参数）。这种"同质结构、异质权重"的性质正是 SGMV 所利用的。

展望未来，多租户 LoRA 问题可能沿两个方向演进。首先，用于推理密集任务的更高秩适配器（数学/代码微调的 rank 64–256）会按比例增加适配器内存占用和 PCIe 加载时间——分页策略需要更激进。其次，带 LoRA 适配器的 MoE 基础模型（Mixtral、Llama 4；见 [../../mistral/mixtral/zh.md](../../mistral/mixtral/zh.md) 和 [../../meta/llama4/zh.md](../../meta/llama4/zh.md)）增加了新维度：每个适配器实例激活的专家因 token 不同而变化，使得适配器级分组困难得多。MoE 路由与多租户 LoRA 的组合截至 2024 年仍是开放的系统问题。
