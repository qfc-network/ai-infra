# 分词：BPE、SentencePiece 与 Tiktoken

- **作者 / 机构**：Sennrich 等（爱丁堡大学） · Kudo & Richardson（Google） · OpenAI
- **发表时间**：BPE: 2016（ACL，arXiv:1508.07909）· SentencePiece: 2018（EMNLP）· Tiktoken: 2023（GitHub）
- **链接**：[BPE 论文](https://arxiv.org/abs/1508.07909) · [SentencePiece 论文](https://aclanthology.org/D18-2012/) · [SentencePiece 代码](https://github.com/google/sentencepiece) · [Tiktoken](https://github.com/openai/tiktoken)

## 一句话总结

分词器将原始 Unicode 文本转化为语言模型可处理的整数序列。字节对编码（BPE）通过迭代合并训练语料中最高频的相邻符号对，学习出一套子词单元词表——既避免了字符级方案的序列过长问题，也规避了词级方案的未登录词（OOV）问题。SentencePiece 在无需预分词的前提下直接在原始 Unicode 文本上训练 BPE，实现了真正的语言无关性。Tiktoken 是 OpenAI 用 Rust 实现的 BPE，服务于 GPT-4/o1，词表规模达 10 万至 20 万。词表大小是一个一阶系统参数：它决定嵌入矩阵的行数，决定固定算力预算能处理多少 token，也决定多语言数据如何在模型的"概念带宽"中分配。

## 背景与动机

### 为什么不用字符或词？

**字符级分词**在任意 Unicode 输入下不存在 OOV 问题，且天然支持所有语言。代价是序列极长——512 个英文单词约有 2500 个字符——模型需要从零学习更高层次的结构，上下文窗口被大量信息量低的 token 占据。

**词级分词**保持序列简短并保留自然语言单元。代价是词表需要覆盖足够多的词汇（英语常需 5 万至 20 万条目），形态变化丰富的语言（芬兰语、土耳其语、阿拉伯语）或专业领域（代码、数学）会进一步膨胀。推理时遇到未见过的词只能替换为单个 `<UNK>` token，丢失所有内部结构。

**子词分词**恰好占据两者之间的甜蜜点：常见词保留为单个 token，罕见词分解为有意义的子词单元，未知词还可以退化为逐字节表示作为兜底。这也是现代大模型普遍采用子词分词的原因。

### 分词的系统级角色

分词器位于所有组件的上游：它决定序列长度，而序列长度驱动几乎所有下游开销——注意力是二次复杂度，KV 缓存内存与序列长度线性相关，预填充吞吐量通常受制于需要处理的 token 数量。一个对同等语料产出多 30% token 的分词器，会让每个下游组件的工作量增加 30%。对于多语言模型，分词器的"生育率"（每字符或每词对应的 token 数）分布不均，实际上让部分语言在每个上下文窗口内能表达的语义概念少得多。

## BPE：字节对编码

### 算法流程

BPE 从单个字符（或字节）的基础词表出发，迭代合并最高频的相邻符号对，直到达到目标词表大小 V：

```
初始化：词表 = {语料中所有单个字符}
对 i = 1..V - |初始词表|：
    统计当前分词语料中所有相邻 (a, b) 对的频次
    (a*, b*) = argmax_{(a,b)} freq(a, b)
    将语料中所有 (a*, b*) 的连续出现合并为新 token "ab"
    将 "ab" 加入词表
```

**核心公式——合并选择：**

```
(a*, b*) = argmax_{(a,b)} freq(a, b)   遍历语料中所有相邻对
```

合并规则在训练语料上学习，推理时按同一优先级顺序确定性地应用。这使 BPE 编码成为一个贪婪的规则重写过程，而非概率模型。

### 工程含义

- **词表大小是超参数**，在训练前确定。典型值：早期模型 3 万至 5 万（GPT-2：50,257），现代大模型 10 万至 20 万。
- **合并规则的顺序至关重要**：同一段文本在推理时之所以能得到完全一致的分词结果，依赖于相同的有序合并规则列表。预训练与微调之间更换分词器会导致模型失效。
- **代码分词**：BPE 会把常见代码模式（`def `、`if `、`return `、`self.`、`print(`）合并为单个 token，为代码模型提供紧凑表示。
- **空格处理**：GPT-2 风格的 BPE 在跟在空格后的 token 前加一个特殊空格字节 `Ġ`（字节 0xC4 0xA0），以区分 " dog" 和 "dog"——这对模型质量很重要，但调试时令人困惑。

### 字节级 BPE

BPE 也可以用全部 256 个字节值初始化，而非 Unicode 字符。这保证了任意字节序列都可分词——彻底消除 OOV。GPT-2 和 Tiktoken 使用字节级 BPE。代价：CJK 字符在 UTF-8 中各占 3 个字节，因此在合并前每个汉字要占 3 个 token。高频 CJK 序列的合并能降低这一开销，但需要较大词表才能将"生育率"降到可接受水平。

## SentencePiece：语言无关分词

### 预分词的问题

大多数 BPE 实现会先按空格对文本做预分词，再在 token 边界内学习合并规则。这隐含了以英语为中心的假设：把空格作为词边界、不考虑词语复合、不考虑黏着形态。日语、中文、韩语词语之间没有空格；泰语同样；阿拉伯语有附着词缀；德语有长复合词。

SentencePiece（Kudo & Richardson，2018）直接在原始 Unicode 文本上训练，不做任何预分词。整个句子（包括空格）被视为 Unicode 码点序列。空格用特殊下划线字符 `▁`（U+2581）表示，使其成为原始文本的可逆字节级编码。

### Unigram 语言模型选项

SentencePiece 同时支持 BPE 和**一元语言模型（unigram）**分词器：
- Unigram 模型从一个大型候选词表出发，迭代删除那些移除后使语料总对数似然增加最少的 token。
- 推理时，Unigram 模型给出所有分词方案的概率分布，取最大后验分词（Viterbi 解码）。
- SentencePiece BPE 是确定性的；Unigram 可以采样——`sentencepiece.encode(..., sample=True)` 从后验中采样一种分词方案，是训练时的一种数据增强形式。

### 在主流模型中的应用

- **Llama 1 / 2**：SentencePiece BPE，词表大小 3.2 万。
- **Llama 3**：SentencePiece BPE，**词表大小 12.8 万**。从 3.2 万扩展到 12.8 万的动机是多语言覆盖和代码密度。与 3.2 万词表相比，中文文本的编码效率提升约 3 倍。
- **T5、mT5**：SentencePiece，词表 3.2 万，Unigram 模型。
- **Gemma**：SentencePiece，词表 25.6 万。
- **DeepSeek V3**：兼容 Tiktoken cl100k_base 的 BPE，词表 10 万。

## Tiktoken：生产环境下的高性能 BPE

Tiktoken 是 OpenAI 的 BPE 分词器，用 Rust 实现，提供 Python 绑定。设计目标是高吞吐量：对于相同词表大小，Rust 实现的速度约为纯 Python HuggingFace 分词器的 3–5 倍。

### 词表系列

| 编码 | 词表大小 | 使用模型 |
|---|---|---|
| `r50k_base` | 50,257 | GPT-3、Codex |
| `cl100k_base` | 100,277 | GPT-3.5、GPT-4、DeepSeek |
| `o200k_base` | 200,019 | GPT-4o、o1、o3 |

`o200k_base` 的词表是 `cl100k_base` 的两倍。对于多语言文本，扩大词表主要带来非拉丁字母文字的压缩率提升。对于英语文本，序列长度仅减少约 5%。

### 性能影响

词表为 20 万的模型，嵌入矩阵形状为 [20 万, d_model]。以 d_model = 7168（DeepSeek V3 规模）、bf16 精度计算：

```
嵌入表大小 = 200,000 × 7,168 × 2 字节 = 2.87 GB
```

对于单卡推理这并不可忽视，但在权重共享模型中嵌入层与解嵌入层（lm_head）共享参数。解嵌入投影是小批量解码时最昂贵的单次操作，因为它是一个 [1, d_model] × [d_model, V] 的矩阵-向量乘积，受内存带宽瓶颈而非计算吞吐量限制。

## Token 预算经济学

### 词表大小权衡

| 词表大小 | 英语字符/token | 中文字符/token | 嵌入参数量（d=4096） | 备注 |
|---|---|---|---|---|
| 3.2 万 | ~0.27 | ~0.8–1.2 | 2.6 亿 | Llama 1/2 |
| 5 万 | ~0.25 | ~0.7–1.0 | 4.1 亿 | GPT-2/3 |
| 10 万 | ~0.23 | ~0.4–0.7 | 8.2 亿 | GPT-4、DeepSeek V3 |
| 12.8 万 | ~0.22 | ~0.3–0.5 | 10.5 亿 | Llama 3 |
| 20 万 | ~0.21 | ~0.25–0.4 | 16.4 亿 | GPT-4o、Gemma |

词表越大 → token 序列越短 → 注意力操作越少、KV 缓存越小 → 推理越快。但嵌入 / 解嵌入矩阵随之增大，且最终投影在小批量下会主导延迟。

### 多语言"生育率"问题

对于英语文本，1 个 token ≈ 0.75 个词 ≈ 4 个字符。对于使用小词表分词器的中文文本，1 个 UTF-8 字符可能需要 1–3 个 token（UTF-8 编码的 CJK 码点占 3 字节）。这意味着：

- 4096 个 token 的上下文窗口大约容纳 2700 个英文单词。
- 同样的窗口在 3.2 万词表下只能容纳 800–1500 个汉字。
- 扩展到 12.8 万词表后，中文生育率改善至约每 2–3 个字符对应 1 个 token。

这一不对称性解释了为什么使用小词表的多语言模型在非拉丁字母语言上系统性地表现不佳：它们每个 token 能处理的语义概念更少，上下文窗口消耗更快。

### 与规模律的联系

[Chinchilla "每参数 20 token"规则](../scaling-laws/en.md)依赖于分词器的选择。一个在字节级分词器下以 3000 亿中文 token 训练的模型，接触到的不同词语和概念数量，远少于使用字符级分词器训练的同等 token 量模型。数据的"信息密度"是分词器生育率的函数，而非原始 token 计数。

## 工程权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| 小词表（3.2 万） | 嵌入参数少；模型分片简单 | 多语言压缩率差；中文/日文每个概念需要 3–4 倍 token |
| 大词表（12.8 万–20 万） | 多语言生育率好；序列更短；相同文本推理更快 | 嵌入 + 解嵌入矩阵更大；小批量下 lm_head GEMV 更慢 |
| 字节级 BPE（Tiktoken、GPT-2） | 零 OOV 保证；覆盖任意字节序列 | CJK 字符在合并前很昂贵（每字 3 字节）；需要较大词表才能实现良好压缩 |
| SentencePiece（无预分词） | 语言无关；直接处理原始 Unicode；可逆编码 | 与带预分词的 BPE 行为略有不同；切换后需重新训练 |
| Unigram 采样分词 | 分词多样性作为数据增强；提升训练鲁棒性 | 非确定性；推理时须用 argmax 解码 |
| 嵌入 / 解嵌入权重共享 | 参数量减半 | 两个矩阵互为转置；与独立矩阵相比质量可能略有下降 |

## 实验结果

**BPE（Sennrich 等，2016）**：证明使用 BPE 子词单元的神经机器翻译模型在英德和英俄翻译上达到或超过词级模型的效果，且不存在 OOV 错误。3 万至 6 万的词表对大多数双语任务已足够。

**SentencePiece（Kudo & Richardson，2018）**：证明将空格视为字符（无预分词）产生的分词结果是无损可逆的——任意 token 序列都可以精确还原为原始文本。这一性质在基于空格的 BPE 中无法保证，因为空格信息可能在分词过程中丢失。

**Llama 3 词表扩展（3.2 万 → 12.8 万）**：Meta 报告称，4 倍的词表扩展使多语言文本的平均序列长度减少约 2.5 倍。中文 token 效率从约 0.8 token/字符提升至约 0.3 token/字符。多语言基准上的下游任务性能大幅提升，这部分归因于分词器改进，部分归因于多语言训练数据的扩充。

**Tiktoken 吞吐量**：Rust 实现在单 CPU 核心上对 `cl100k_base` 的分词吞吐量约为 10 MB/s，而等效 Python 实现约为 2–3 MB/s。在数据预处理阶段（多 TB 语料），这一差距非常显著。

## 综合评述

分词是任何大模型流水线中第一个有损压缩步骤，其选择以难以逆转的方式影响所有下游组件。一个对目标语言不友好的分词器，实际上将模型针对该语言的上下文容量减半——每个 token 能携带的概念更少，上下文窗口消耗更快，即便 Transformer 本身训练良好，基准测试上也会显得较弱。这正是 Llama 3、Gemma 和 Qwen 等模型相比前代大幅扩展词表的原因之一。

词表大小与嵌入矩阵构成推理时的经典空间-算力权衡。lm_head 的矩阵乘法（[批量×序列, d_model] × [d_model, V]）是每个解码步骤中对于小批量最昂贵的单次操作。批量大小为 1、d_model = 8192、V = 12.8 万时，这是一次每步需要约 2 GB 带宽的矩阵-向量乘积——在大多数硬件上主导解码延迟。投机解码需要对草稿 token 在目标模型的 logit 上做验证，会进一步放大这一开销。词表越大，lm_head 越昂贵，但序列长度减少，因此对端到端延迟的净影响取决于序列长度和批量大小。

更深层的工程教训是：分词器是一种在训练开始前就必须确定的基础设施承诺，事后几乎无法更改。模型无法在训练后重新分词——若强行替换分词器，就必须完全重训。这使分词器的选择类似于训练方案的硬件选型：你将在模型的整个生命周期内承受其后果。业界已逐步收敛到 10 万至 20 万词表的 BPE，但最优选择仍取决于具体工作负载——以代码为主的模型与以对话为主的模型，在合并频率分布上有不同需求。
