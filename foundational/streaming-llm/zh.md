# StreamingLLM 与注意力汇聚点

- **作者 / 机构**：Xiao 等（MIT、CMU、MIT-IBM Watson AI 实验室）
- **发表时间**：2023-09（arXiv:2309.17453）
- **链接**：[论文](https://arxiv.org/abs/2309.17453) · [代码](https://github.com/mit-han-lab/streaming-llm)

## 一句话总结

标准滑动窗口注意力只保留最近 W 个 token 的 KV 缓存，但当序列的初始 token 滑出窗口时会灾难性失效——即使最近的上下文完好无损，困惑度也会骤增。根源在于**注意力汇聚点现象**：初始 token（尤其是位置 0）无论语义内容如何，都会在几乎所有注意力头中积累到极不成比例的注意力权重，充当 softmax 概率质量的"垃圾桶"。StreamingLLM 的修复方案极为简洁：在滑动窗口之外，始终保留前 K_sink 个 token（通常为 4 个）的 KV 缓存条目。这以固定大小（K_sink + W_recent）的 KV 缓存恢复了稳定的无限长生成——无论序列多长，内存占用恒定不变。本文通过将无限序列问题重构为有界缓存调度问题，使在普通硬件上运行连续多轮对话、长程智能体和流式推理成为可能。

## 背景与动机

### 服务端的现实缺口：大模型需要什么 vs. 推理能提供什么

大模型以固定最大上下文长度训练（如 LLaMA 为 4096 token，LLaMA 2 为 8192 token）。在生产环境中，两类使用场景会超出这一限制：

1. **多轮对话**：长对话快速积累 token。100 轮 × 每轮 200 token = 2 万 token——是 LLaMA 训练长度的 5 倍。
2. **流式文档处理**：对连续数据流的实时摘要、转录或分析。

在这些长度下，**全注意力**不可行：KV 缓存内存与序列长度线性增长。对于 32 层、32 个 KV 头、头维度 128、bf16 精度的 70 亿参数模型：

```
每 token 的 KV 缓存 = 32 × 2 × 32 × 128 × 2 = 524,288 字节 ≈ 0.5 MB/token
```

2 万 token 时，单序列 KV 缓存达 10 GB——等于一张标准 A10G GPU 的全部内存。

**朴素方案的失效模式**：
- *从头重新编码*：极慢——模型每步生成都需处理所有先前 token。
- *截断旧 token*：简单，但模型丢失早期上下文，多轮对话中意味着遗忘早期对话内容。
- *滑动窗口*：只保留最近 W 个 token。这看起来合理——如果旧 token 离当前查询很远，删掉它们为何有害？

### 为什么滑动窗口失效：实验观察

Xiao 等在生成最长 10 万 token 的序列时测试了 LLaMA-2-7B 的滑动窗口注意力（窗口大小 W）。发现：只要 token 0 还在窗口内，困惑度保持稳定；一旦 token 0 滑出窗口，困惑度飙升 10–100 倍，连贯性完全崩溃——尽管最近的 W 个 token 仍然可用。

这是一个反直觉的失效。模型并不需要初始 token 的**内容**——它需要初始 token 提供某种别的东西。

## 注意力汇聚点现象

### 实验观察

可视化自回归大模型的注意力模式，可以发现一个一致的规律：初始 token（尤其是 token 0，以及通常前 3–4 个 token）在几乎所有注意力头、所有层中，对于大多数查询位置，都获得了极不成比例的高注意力权重。这与初始 token 的语义内容无关——即使初始 token 是语义空洞的分隔符如 `\n` 或 `<s>`，这一现象同样存在。

这就是**注意力汇聚点**：初始 token 充当"排水口"，多余的 softmax 概率质量积聚于此。

### 汇聚点形成的原因：softmax 约束

Softmax 在所有键上的权重之和必须为 1。在多对一注意力场景中（一个查询关注 N 个键），并非所有键都语义相关。但模型无法输出零注意力——softmax 没有"空"选项。当滑动窗口内的内容与当前查询无关时（例如当前查询的答案不在窗口内），概率质量必须流向某处。它流向了"最无害"的位置：初始 token。

这是**训练阶段产生的工件**。训练时，模型在完整序列上学习，对初始 token 的注意力如果导致错误预测就会被惩罚。但当没有相关键可用时，模型学会了把概率质量"停放"在初始 token 上——这些 token 在所有训练序列中都存在——这是安全的做法。汇聚 token 积累注意力，是 softmax 归一化与对无关上下文注意力相互作用的学习工件。

实验数据：token 0（`<s>` 或 BOS）在各头和各层上始终获得 5–20% 的总注意力质量。token 1–3 的注意力权重也显著偏高。中间位置真正有信息量的 token 得到的注意力比例相应偏低。

### 后果：为什么删除汇聚点会破坏生成

当滑动窗口驱逐初始 token 时，模型的 softmax 失去了惯用的"停车位"。概率分布以非预期的方式崩溃到可用 token 上，破坏注意力模式。这一效应跨层级联：早期层的 softmax 扭曲导致后续层产生扭曲的键/值表示。模型输出不连贯文本。

## StreamingLLM：解决方案

### 算法

StreamingLLM 通过两个组件的组合，维持恒定大小的 KV 缓存：

1. **汇聚 token**：始终保留前 K_sink 个 token 的 KV 缓存条目（论文中 K_sink = 4）。这些条目永不被驱逐。
2. **滑动窗口**：保留最近 W_recent 个 token（如 2048 或 4096 个）。

总 KV 缓存大小 = K_sink + W_recent，**与序列长度无关**。

**KV 缓存大小公式：**

```
KV 缓存内存 = (K_sink + W_recent) × 层数 × 2 × 头维度 × KV 头数 × 每元素字节数
```

对于 70 亿参数模型（32 层，32 个 KV 头，头维度 128，bf16），K_sink=4，W_recent=2048：

```
= (4 + 2048) × 32 × 2 × 128 × 32 × 2 = 1.07 GB
```

这是固定值。无论生成 10 个 token 还是 1000 万个 token，KV 缓存始终占用 1.07 GB。

### 保留汇聚 token 的位置编码

一个实现细节：当汇聚 token 位于原始位置 0–3，而最近 token 位于位置 50,000–52,047 时，RoPE 编码使用的位置 ID 必须正确处理。汇聚 token 保留其原始位置 ID（0–3）。最近 token 使用其原始位置 ID（50,000–52,047）。缓存中的顺序是不连续的，但位置编码是一致的。

这至关重要：如果位置 ID 被朴素地重新从 0 开始索引，模型会因遇到曾经见过的位置而产生混乱。汇聚 token 必须保持其"位置 0–3 token"的身份。

### 每步的注意力计算

每次解码步骤：
1. 新 token 关注：[汇聚 token 的 KV 条目] ++ [最近窗口的 KV 条目]。
2. 计算新 token 的键/值并追加到最近窗口。
3. 若最近窗口已满（大小 > W_recent），先入先出地驱逐最早的条目。
4. 永不驱逐汇聚 token 条目。

注意力模式是稀疏的：新 token 看到 K_sink + W_recent 个先前 token，而非所有先前 token。

### 丢失的信息

StreamingLLM **不提供**真正的长程记忆。已滑出最近窗口且不在初始汇聚 token 中的信息将永久丢失。模型无法回答 10 万个 token 之前发生的事情（除非它们恰好在前 4 个 token 中，这在实际场景中通常无用）。

该方法的主张更为有限：StreamingLLM 使**稳定生成**能够在无限长流上进行，而不会产生 KV 缓存爆炸。窗口之外的内容不可访问，但生成不会变得不连贯。这使其适用于：
- **多轮对话**：通常不需要早期轮次的逐字内容，只需其结论。
- **流式摘要**：模型持续对最近 W 个 token 做摘要。
- **长程智能体**：只有最近状态重要的场景。

对于需要**跨窗口回忆**的任务（如"你在对话早期提到过 X"），StreamingLLM 不够用——信息已经消失。完整上下文检索需要 RAG、记忆模块或上下文压缩技术。

## 与相关方案的对比

| 方案 | KV 缓存大小 | 无限长时的连贯性 | 保留信息 | 备注 |
|---|---|---|---|---|
| 全注意力 | O(L)——无界增长 | 超出训练长度时退化 | 所有 token | 超出 L_train 需 PI/YaRN |
| 朴素滑动窗口 | O(W)——有界 | token 0 滑出时崩溃 | 最近 W 个 token | 没有汇聚修复则失效 |
| StreamingLLM | O(K_sink + W)——有界 | 无限期稳定 | 前 K_sink 个 + 最近 W 个 | 本论文 |
| H2O / Scissorhands | O(预算)——有界 | 稳定 | 预算内最重要 token | 需要追踪注意力分数 |
| SnapKV | O(选择量)——有界 | 稳定 | 聚类后的重要 KV 条目 | 离线选择；适用场景不同 |
| RAG / 记忆模块 | KV 有界，检索 O(全部) | 稳定 | 全部（通过检索） | 检索延迟；独立系统 |

StreamingLLM 是最简单的方案，且连贯性保证最强。代价是窗口外信息的硬丢失。

## 工程影响

### 规模化多轮对话服务

使用 70 亿参数模型并发服务 1000 路多轮对话：

- 全注意力：1000 × 约 1 万 token × 0.5 MB/token = 5 TB KV 缓存。不可能。
- StreamingLLM（W=2048，K_sink=4）：1000 × 1.07 GB = 1.07 TB。仍然很大，但通过将 KV 卸载到主机 DRAM 可以实现。
- StreamingLLM（W=512，K_sink=4）：1000 × 275 MB = 275 GB。可以容纳在标准 8×A100 节点上。

### 与 KV 缓存量化的结合

StreamingLLM 的有界缓存与 KV 缓存量化（见 [kv-cache-quantization 条目](../kv-cache-quantization/zh.md)）自然结合。采用 4 位 KV 量化后，上述 275 GB 降低至 140 GB。汇聚 token 可以保持较高精度（fp16），因为它们被频繁访问；最近窗口可以使用 4 位量化。这种"混合精度流式 KV"是实用的生产模式。

### 与分页注意力的结合

PagedAttention（见 [paged-attention 条目](../paged-attention/zh.md)）将 KV 缓存作为固定大小的块管理。StreamingLLM 的 K_sink + W_recent 预算可以干净地映射到固定块分配上：为 K_sink 分配块（小型永久预留）加上滑动窗口对应的 W_recent / block_size 个块。FIFO 驱逐策略映射为块回收。

## 工程权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| 保留 K_sink=4 个初始 token | 稳定的注意力分布；防止困惑度爆炸 | 每序列额外 4 个 KV 条目（开销可忽略） |
| 固定窗口大小 W | 有界 KV 缓存内存；可预测的内存分配 | 超出 W 的信息永久丢失 |
| 保留原始位置 ID（不重新索引） | 正确的 RoPE 行为；避免位置混乱 | 缓存索引不连续；内核稍复杂 |
| 无需微调的流式推理 | 适用于预训练模型；无需额外训练 | 模型在 L_train 下训练；对于长序列，质量不如经过微调的长上下文模型 |
| FIFO 驱逐（最旧的 token 先出） | 简单；无评分开销；可预测 | 不保留语义重要的窗口中部 token；H2O/Scissorhands 风格的重要性评分可以做得更好 |
| 不使用记忆模块 / RAG | 系统简单；无检索延迟 | 真正的长程回忆需要外部系统 |

## 实验结果

**长生成的困惑度**：LLaMA-2-7B、LLaMA-2-13B、Falcon-7B、Pythia 6.9B。K_sink=4、W=2048 的 StreamingLLM 在最长 400 万 token 的序列上保持恒定困惑度。相同 W 但无汇聚 token 的朴素滑动窗口，在 K_sink 个 token 离开窗口的瞬间出现困惑度爆炸。全注意力在超出训练长度后困惑度逐渐上升。

**汇聚 token 消融**：K_sink 从 4 减少到 1 会降低稳定性。K_sink=1（仅 BOS token）在大多数模型上有效。K_sink=0（纯滑动窗口）失效。K_sink=4 在所有测试模型上均鲁棒。论文还表明，"学习汇聚"（在训练时预置一个专门指定为汇聚点的哨兵 token）可以减少对 K_sink 大小的需求，但需要重新训练模型。

**吞吐量**：StreamingLLM 处理 400 万 token 流的吞吐量与 W=2048 的固定上下文推理几乎相同。由于 KV 缓存有界，随着生成长度增加，不存在内存碎片或重新分配开销。

## 综合评述

注意力汇聚点是大模型系统文献中较为清晰的洞见之一：实验观察（初始 token 获得高注意力）→ 机制解释（softmax 必须归一为 1；初始 token 是学习到的"空注意力"目标）→ 最小化工程修复（保留 K_sink=4 个初始 token）。这个修复在内存和算力上几乎零代价，却彻底解决了滑动窗口的失效模式。

更深层的启示是：大模型内部包含训练配置产生的学习工件，这些工件在短上下文基准测试中完全不可见，却在生产环境中成为承重结构。注意力汇聚点就是一例：它从未在标准评估中被测试，从未在损失曲线中被提及，却是支撑整个生成过程的承重梁。系统工程师需要了解它的存在。

StreamingLLM 占据了一个特定的细分场景：以有界内存进行无限长生成，无需额外训练，保证连贯性，代价是窗口外信息的硬丢失。这使它成为流式推理使用场景的合适工具，也是设计多轮服务基础设施时重要的思维模型。对于需要长程回忆的使用场景，[位置内插技术](../position-interpolation/zh.md)结合[分页注意力](../paged-attention/zh.md)和[KV 缓存量化](../kv-cache-quantization/zh.md)是合适的技术栈。两种方案互补：一种扩展可以持有的窗口，另一种接受有界窗口并优雅地处理它。
