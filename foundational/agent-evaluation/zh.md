# 代理评估基础设施

- **核心基准**：SWE-bench（普林斯顿 NLP，2023）、TAU-bench（Sierra AI，2024）、WebArena（CMU，2023）
- **链接**：[SWE-bench](https://www.swebench.com) · [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/) · [WebArena](https://webarena.dev) · [TAU-bench (arXiv:2406.12045)](https://arxiv.org/abs/2406.12045)

## 概述

评估代理在结构上比评估语言模型更困难。语言模型评估针对已知正确输出衡量单次响应的质量；代理评估针对随每个动作发生变化的环境衡量多步轨迹的质量。最终结果的正确性与轨迹的正确性并不等同——代理可能偶然得到正确答案，也可能在每步都做出合理决策后仍然失败。代理循环中的错误复合特性意味着，每步 10% 的错误率在 10 步后会变成 65% 的失败率。三个基准已成为规范的评估平台：SWE-bench（代码代理）、TAU-bench（工具使用对话代理）、WebArena（基于浏览器的任务完成）。每个基准都有独特的基础设施需求和失败模式，没有任何一个能完全覆盖真实世界代理任务的生产分布。

## 为何代理评估更困难

标准语言模型基准（MMLU、HumanEval、MATH）给出静态的（输入，预期输出）对。模型的任务是生成响应，评估仅是该响应的函数。当应用于代理时，这种方式在多个维度上失效：

**轨迹依赖性**：代理在第 5 步的动作取决于前 4 步产生的状态。可能轨迹的空间随步骤数指数增长。不存在唯一"正确"的轨迹——只有正确（和错误）的最终状态。

**误差复合放大**：设每步正确的概率为 `p`，则在独立假设下，N 步任务成功完成的概率至多为 `p^N`，在误差相关的情况下更低。当 `p = 0.9`、N = 10 时，成功概率至多为 35%。这意味着评估结果对单个错误模式的敏感程度远超单次响应基准。

**环境非确定性**：真实环境会发生变化。网页更新布局，API 端点返回不同数据，出现网络超时。在评估日通过的任务可能在部署日因与代理质量无关的环境原因而失败。确定性环境控制是评估基础设施的重要组成部分。

**部分得分**：对于一个 20 步任务，代理在失败前正确完成了 18 步，二元通过/失败会丢失大量信号。分级轨迹指标是必要的，但引入了自身的校准问题。

**评判可靠性**：当成功标准无法机械验证时（例如"给这位客户写一封专业邮件"），需要第二个 LLM 充当评判者。LLM 评判者存在系统性偏差——倾向于偏好来自更大模型的响应，无论质量如何都会惩罚不寻常的格式，并对评估标准的表述方式敏感。

## SWE-bench

### 测量内容

SWE-bench（软件工程基准）包含来自 12 个真实 Python 代码库（Django、Flask、sympy、scikit-learn、pytest、astropy 等）的 **2,294 个 GitHub 问题**。每个实例是一个（特定提交时的代码库状态、问题文本、金标准补丁、测试套件）元组。代理的任务是生成一个代码补丁，应用于该提交时的代码库后，能使原本失败的测试通过，且不破坏之前通过的测试。

"Verified"子集（SWE-bench Verified，500 个实例）经人类软件工程师手动审核，确认问题描述明确且金标准补丁是唯一合理的修复方案。这个子集是规范排行榜，因为完整的 2,294 个实例集包含噪声：问题描述不充分，或金标准补丁只是多个有效解决方案之一。

截至 2026 年初的典型顶级得分：最佳公开报告系统（Claude 3.5 Sonnet + 脚手架、GPT-4o + 脚手架、开源代理）在 SWE-bench Verified 上达到 **48–55%**。100% 的上限不是理论限制——有些问题确实存在连专家人类也会争议的模糊修复方案。

### 基础设施需求

运行 SWE-bench 需要：

1. **每个实例的代码库沙箱**：一个 Docker 容器，在指定提交时检出代码库并安装所有依赖项。每个唯一代码库的设置可能需要 2–10 分钟；通常预先烘焙到基础镜像中。2,294 个实例跨 12 个代码库，完整评估需要运行数百个唯一容器实例。

2. **测试执行框架**：代理生成补丁后，应用补丁（`git apply`），运行测试套件（按各代码库配置运行 `pytest`），并解析结果。给定补丁，通过/失败判定是确定性的。测试执行时间因代码库而异，从 10 秒到 10 分钟不等。

3. **代理执行沙箱**：代理本身也运行在容器中，配备读取文件、写入文件、运行 bash 命令和搜索代码库等工具。代理在评估期间不得访问互联网（防止检索金标准补丁）。上下文窗口管理至关重要——大型代码库可能有数千个相关文件；代理必须高效地导航其中。

4. **成本预算**：使用前沿模型进行单次完整 SWE-bench Verified 运行的 API 调用成本为 **200–600 美元**，具体取决于模型、脚手架架构以及上下文管理的激进程度。每周以完整规模进行评估的团队需要专门的预算项。

SWE-bench 评估框架是开源的。最小自托管设置需要约 50 GB 存储（预构建的 Docker 镜像）和多核机器以并行运行评估（通常同时运行 16–32 个容器，在 2 小时内完成完整评估）。

### SWE-bench 不测量的内容

SWE-bench 仅测量代码补丁能力。它不涵盖：从空文件规范编写新功能、无错误报告的重构、跨代码库更改、编写测试，或任何不需要解决现有测试套件中现有问题的软件工程任务。它还测量 Python 生态系统的快照；代理可能学会针对特定代码库的习惯用法进行优化。

## TAU-bench

### 测量内容

TAU-bench（工具-代理-用户基准）模拟**客户服务场景**。每个回合涉及三个组件：

1. **用户模拟器**：一个扮演具有特定请求和私有"真值"状态的客户的 LLM（客户的真实需求不直接告知代理）；
2. **策略文档**：描述代理必须遵守规则的纯文本文档（例如"购买后 30 天内允许退款"；"航班变更需支付 150 美元费用，除非客户具有白金会员资格"）；
3. **工具集**：代理可以进行的结构化 API 调用，用于查询订单、修改预订、发起退款等。工具具有真实的延迟，可能返回错误。

代理的任务是在多轮对话中，仅使用可用工具，在遵守策略的前提下正确解决用户的请求。TAU-bench 有两个领域：**零售**（订单管理、退货、产品问题）和**航空**（机票预订、变更、取消、升舱）。

成功通过两个标准衡量：代理的最终动作是否正确解决了用户的请求（任务完成），以及回合中采取的所有动作是否符合策略文档（策略遵守）。完成率高但遵守率低的代理在钻空子；遵守率高但完成率低的代理过于保守。两个维度都是必要的。

典型得分：顶级代理在**零售领域的任务完成率为 70–80%**，在航空领域稍低（策略更复杂）。前沿模型的策略遵守率通常为 85–95%，但在边缘情况和罕见策略条款上会急剧下降。

### 基础设施需求

TAU-bench 在整个评估过程中需要一个实时 LLM 作为用户模拟器，这使 API 成本相比单模型评估翻倍。用户模拟器必须是能够进行真实多轮对话并一致维护真值状态的模型；GPT-4 级别是标准选择。策略文档和工具集是确定性的；用户模拟器引入随机性。可重现性要求将用户模拟器的温度固定为零，或运行多个随机种子并报告均值 ± 方差。

## WebArena

### 测量内容

WebArena 在 Docker 容器中本地部署**六个真实 Web 应用程序**：电商网站（基于 Magento）、论坛（Reddit 克隆）、代码仓库（GitLab）、协作 Wiki（Confluence 克隆）、地图应用和管理仪表板。任务是需要多步浏览器交互才能完成的自然语言指令："找到 50 美元以下最便宜的红色连衣裙并加入购物车"、"提交一个修复 linux-kernel 仓库 README 中拼写错误的 PR"、"找出用户'alice'所有提到 Python 的帖子"。

成功通过功能性状态检查衡量：购物车中是否包含正确商品？是否开启了包含修复拼写错误的差异的 PR？给定固定的应用状态，这些检查是程序化且确定性的。

评估包含跨六个应用的 **812 个任务**，难度各异。前沿模型配合浏览器自动化脚手架的典型得分为 **30–45%**。相同模型在 SWE-bench（约 50%）和 WebArena（约 35%）之间的分数差距，反映了视觉 UI 导航相比结构化代码编辑的额外难度。

### 基础设施需求

WebArena 需要同时运行六个容器化 Web 应用程序和一个浏览器自动化环境。总内存占用：每台评估机器约 8–16 GB RAM。通过数据库快照在回合间重置应用状态；根据应用不同，每回合重置时间为 5–30 秒。在单台机器上以单个并发回合运行完整 812 个任务的评估需要 4–8 小时；跨多台机器的并行执行成比例缩短时间。

WebArena 的浏览器自动化使用 Playwright 或 Selenium；代理根据脚手架不同，以页面可访问性树（HTML 元素 + ARIA 属性）或截图作为观测。基于可访问性树的代理更快（无视觉编码成本），但会遗漏视觉信息；基于截图的代理更慢，但对可访问性标记质量差的页面更健壮。

## 评估基础设施需求总结

在所有三个基准中，共同的基础设施需求包括：

**每回合的沙箱执行**：每个回合必须从干净、确定性的状态开始。带有快照数据库或 Git 代码库的 Docker 容器是标准方案。回合间的状态泄漏（例如，前一个代理的动作持续到下一回合）会使基准失效。

**轨迹日志记录**：每回合的所有工具调用、LLM 输入和输出、中间状态以及时序数据都必须被记录。这是主要的调试产物。没有轨迹日志，40% 的成功率只是一个不透明的数字；有了轨迹日志，它分解为"15% 失败是因为代理找不到相关文件"、"10% 失败是因为代理的补丁有语法错误"、"15% 因其他原因失败"——每个都有清晰的改进路径。

**自动成功检测**：成功标准必须通过程序化方式评估。在规模化场景下的人工评估（2,294 个 SWE-bench 实例 × 每周多次代理运行）不实际。对于 SWE-bench，测试套件的通过/失败是检测器；对于 WebArena，数据库状态断言是检测器；对于 TAU-bench，工具调用日志检查与用户模拟器满意度分数的组合被使用。

**每次运行的成本跟踪**：API 成本必须按回合而非按运行跟踪。以 $2/回合解决 50% SWE-bench 的代理与以 $10/回合解决 50% 的代理具有完全不同的成本效益轮廓。

## 轨迹级指标

二元通过/失败是所有三个基准的主要报告指标，但它丢弃了大量信号。补充性轨迹指标包括：

**步骤效率**：

```
效率 = 成功率 / 每次成功回合的平均步骤数
```

用 5 步解决任务的代理比用 15 步解决的代理更高效，即使成功率相同。步骤效率惩罚冗长的、对冲式的代理。

**工具调用精确率**：有效调用（schema 正确）且产生有用信息（非错误或无关结果）的工具调用比例。高精确率的代理在对上下文窗口无贡献的工具调用上浪费更少 token。

**部分进度**：对于多步任务，根据到达中间里程碑给予部分得分的任务完成分数。WebArena 中较难的任务（需要 5 步以上）在二元通过/失败上难以区分；部分得分更加敏感。

**恢复率**：在代理至少犯了一个可恢复错误的回合中（例如，调用了错误的工具、误读了某个值），代理检测到错误并成功恢复的比例。这衡量对不完美感知的鲁棒性，而非仅衡量理想条件下的准确率。

## 开放式任务的 LLM 评判

对于成功标准无法完全机械规定的任务——特别是 TAU-bench 和自定义生产评估——一个独立的 LLM 充当轨迹的评判者。评判者接收任务规范、完整轨迹和评分标准，输出分数。

LLM 评判者存在几种失败模式：

- **长度偏差**：在其他条件相同的情况下，评判者倾向于给较长的响应更高分；
- **自我增强偏差**：与被评估代理同属一个模型系列的评判者，对该代理输出的评分更高；
- **标准敏感性**：改变标准的表述方式（例如"从 1–5 评分"与"从 1–10 评分"）会在不改变底层质量的情况下改变分数；
- **校准漂移**：如果没有明确的校准数据，LLM 评判者不与人类标签校准。在分布内任务上与人类一致性相关系数为 0.85 的评判者，在分布外任务类型上可能降至 0.60。

缓解措施包括：收集（轨迹，人类标签）对作为校准集；针对此校准集微调或优化提示工程评判者；将评判者间一致性作为可靠性的代理指标；绝不使用评判模型自身所属系列来评判该模型的代理。

代理轨迹的 LLM 评判在结构上类似于应用于推理链的过程奖励模型（PRM）：评判者对中间步骤的质量进行评分，而不仅仅是最终答案（参见 [../process-reward-models/](../process-reward-models/)）。区别在于：PRM 通常在步骤级人类标签上微调并输出校准概率；LLM 评判者通常通过提示调整并输出自然语言分数。对轨迹评判者进行 PRM 风格的微调是 2025–2026 年的活跃研究方向。

## 基准饱和及其后果

SWE-bench Verified 得分快速攀升：从约 20%（2023 年底基线）到约 50%（2026 年初前沿水平）。随着分数接近上限（根据人类工程师表现估计约为 70–80%），基准效用下降——它不再能区分顶级系统。后果包括：

- **分布偏移**：针对 SWE-bench Python 代码库优化的系统，在其他语言（TypeScript、Rust、Java）、其他代码库结构或具有不同约定的真实生产代码库上可能泛化效果差；
- **基准过拟合**：针对 SWE-bench 调整的训练数据和脚手架选择可能不反映真正的软件工程能力；
- **需要更难的划分**：SWE-bench++ 和领域特定变体（TypeScript 版、基础设施即代码版 SWE-bench）正在涌现，以在标准基准饱和后保持信号价值。

同样的动态也适用于 WebArena，自发布以来得分从约 10% 上升到约 40%。社区的通常应对是添加更难的任务变体、新的应用环境，或转向无法直接针对训练的私有保留集。

## 工程权衡

| 评估方案 | 任务类型 | 环境复杂度 | 可重现性 | 每次运行成本 | 生产相关性 |
|---|---|---|---|---|---|
| SWE-bench Verified | 从错误报告进行代码补丁 | 中（沙箱 Python 代码库） | 极高（确定性测试套件） | $200–600（500 个实例） | 代码代理高；仅限 Python 开源 |
| TAU-bench | 客户服务、策略遵守、工具使用 | 低（模拟工具 + LLM 用户） | 中（用户模拟器引入方差） | $50–150（零售 + 航空） | 企业对话代理高 |
| WebArena | 端到端浏览器任务完成 | 高（6 个实时 Web 应用，完整浏览器） | 中（应用状态重置，页面渲染方差） | $100–300（812 个任务） | 浏览器自动化高；仅限标准 Web 应用 |
| 自定义内部评估 | 生产任务分布 | 可变 | 高（如果有确定性固件） | 可变 | 最高——与实际部署匹配 |

实践建议是将 SWE-bench 和 WebArena 作为外部校准信号（与已发布基线对比），并为生产任务分布构建自定义内部评估。已发布基准测量通用能力；内部评估测量部署特定能力。两者之间的差距是判断有能力的代理能否在生产中实际工作的最重要诊断指标。
