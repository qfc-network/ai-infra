# 前缀缓存

_系统设计条目，聚焦跨请求的 KV cache 复用。匹配算法（RadixAttention）详见 [SGLang 条目](./sglang/)；本文聚焦设计空间：匹配策略、淘汰策略、命中率经济学、多级缓存以及与解耦服务的集成。_

- **主要实现**：vLLM Automatic Prefix Caching（APC，2024）、SGLang RadixAttention（2023）、TensorRT-LLM KV cache 复用（2024）
- **基础工作**：Zheng 等（SGLang，arXiv:2312.07104）；vLLM 文档（APC）；Mooncake（arXiv:2407.00079）

## 一句话总结

每一个与先前请求共享 token 前缀的 LLM 推理请求，都可以跳过该前缀的 KV cache 重计算——直接复用先前请求的缓存。在生产 LLM 服务中，前缀并非随机的：系统提示在每个请求中重复出现，few-shot 示例在数据集中共享，检索上下文在会话中反复出现，Agent 脚手架出现在每次调用中。前缀缓存将这种结构转化为可量化的吞吐和延迟收益：一个 1,000 token 的系统提示命中缓存后，每个请求节省 1,000 token 的 prefill 计算，对常见部署可将首 token 延迟（TTFT）降低 50–80%。设计空间有三个维度：**匹配策略**（如何识别可复用的 block）、**淘汰策略**（GPU 内存耗尽时淘汰哪个 block）以及**缓存层级**（仅 GPU HBM，还是溢出至 CPU DRAM 和磁盘）。每个维度都涉及非显而易见的权衡。

## 背景与动机

### 前缀重复的来源

PagedAttention（[条目](./paged-attention/)）确立了 KV cache block 是内存管理的正确物理单位。block 间的写时复制实现了束搜索的共享。下一步：跨*请求*共享 block，而非仅在一个请求的束搜索树内共享。

真实流量在多个层面具有高度前缀重复性：

| 重复类型 | 示例 | 典型前缀长度 |
|---|---|---|
| 系统提示 | "你是一个有帮助的助手。请不要……" | 50–500 tokens |
| Few-shot 示例 | 带 5 个标注示例的分类 | 200–2,000 tokens |
| RAG 上下文 | 检索文档前置于每个查询 | 500–8,000 tokens |
| Agent 脚手架 | 工具描述、环境状态 | 500–5,000 tokens |
| 多轮历史 | 对话的早期轮次 | 随轮次增长 |
| 数据集批量处理 | 数千条数据项上相同的指令 | 100–2,000 tokens |

每种情况下，前缀都在每个请求中被重新计算——纯粹浪费 prefill 算力和 TTFT 延迟。

### 收益规模

在 H100 上运行 70B 模型，prefill 吞吐约为每秒 10,000–20,000 tokens（算力瓶颈，批量处理）。一个 2,000 token 的共享系统提示 + RAG 上下文，无缓存时每个请求的 prefill 耗时 0.1–0.2 秒。100% 前缀缓存命中时，这一成本降至接近零。在 100 请求/秒的负载下，每秒节省 10–20 GPU 秒——对共享部分而言，相当于免费获得 10–20 倍的 prefill 容量倍增。

## 核心方法

### 匹配单位：block

PagedAttention 的 block 抽象（固定大小的 KV cache 页，通常每 block 16–32 tokens）是前缀匹配的自然单位。当且仅当某前缀所属的完整 block 已被之前计算且仍在内存中时，该前缀才可复用。

匹配粒度有一个推论：不在 block 边界结束的前缀只能部分缓存。最后一个不完整 block 必须重新计算。对于 block 大小 16 tokens、系统提示 100 tokens 的情况：
- Block 0–5（token 0–95）：完全可缓存——复用 6 个 block
- Block 6（token 96–100）：不完整——必须从其起始处重新计算

这就是**分块 prefill**（[条目](./chunked-prefill/)）与前缀缓存相互促进的原因：分块 prefill 允许服务器用新请求的 token 填满不完整的 block，使其对下一个共享该前缀的请求可缓存。

### 策略一 — 基于哈希的 block 匹配（vLLM APC）

vLLM 的自动前缀缓存对每个 block 的内容计算**哈希**（block 的 16 个 token ID 加上前一个 block 的哈希，形成链式哈希）。新请求到达时：

1. 顺序对其提示的每个 block 计算哈希。
2. 在全局 block 哈希表中查找每个哈希。
3. 若找到（且 block 仍在内存中），跳过重新计算——在请求的 block 表中标记为"复用"。
4. 第一次缓存缺失时停止——后续所有 block 也是缺失（前缀属性：只有前序 block 全部命中，当前 block 才可复用）。

链式哈希确保了相同内容的 block 在提示不同位置时被视为不同（位置 3 的"the cat"与位置 100 的"the cat"哈希不同），防止偶发的上下文外复用。

**复杂度**：每个请求 O(前缀长度 / block 大小) 次哈希查找。使用哈希表时，每次查找为 O(1)。相比 prefill 成本，开销可忽略不计。

**局限性**：仅精确匹配。中间任何一个 token 不同的前缀会从该点起触发完全缓存缺失，即使后缀与先前请求完全相同。无模糊匹配或语义相似度——单位是 token ID 的精确字节相等。

### 策略二 — 基数字典树匹配（SGLang RadixAttention）

SGLang 将缓存 block 存储在以 token ID 序列为索引的**基数字典树**（压缩前缀树）中。完整细节见 [SGLang 条目](./sglang/)。与哈希匹配的关键区别：

- 基数树使**最长前缀匹配**显式且高效：从根节点一次遍历即可找到与新请求匹配的最长缓存前缀。
- 树结构使淘汰决策更廉价：淘汰一个子树可原子性地删除一族相关前缀，无需扫描整个缓存即可维护字典树不变量。
- 树直接暴露**共享拓扑**：同一节点的分支共享该节点的前缀，使写时复制和缓存计费变得直接。

**复杂度**：查找 O(前缀长度)，但对长前缀而言常数因子优于哈希链——字典树在第一次不匹配时自然停止，无需为所有 block 计算哈希。

### 淘汰策略

当 GPU HBM 已满且需要分配新 block 时，缓存管理器必须淘汰现有 block。淘汰策略决定淘汰哪个 block。

**LRU（最近最少使用）：**
淘汰最久未被访问的 block。标准、研究充分、用双链表 + 哈希表易于实现。访问模式以近因性为主时表现良好（近期请求很可能很快再次出现）。

失效场景：偶尔被访问的单个超大前缀（被 1% 流量使用的 10,000 token RAG 上下文）会在缓存中存活，挤出许多更小、更频繁使用的前缀。

**带衰减的 LFU（最不频繁使用，含指数衰减）：**
近期访问权重高于远期。淘汰衰减访问计数最低的 block。对同时包含频繁短前缀和偶发长前缀的混合工作负载更好。

失效场景：新前缀初始频率低，立即被淘汰，导致新系统提示的冷启动惩罚。

**大小感知淘汰：**
内存压力下优先淘汰大 block（或大子树），每次淘汰决策回收的内存最大化。权衡：可能淘汰恰好体积大、使用频繁的前缀，而这些前缀重计算成本最高。

**实践选择**：大多数生产系统以 LRU 为默认。对于有少数主导系统提示的工作负载（常见情况），LRU 接近最优——系统提示在每个请求上被访问，任何近因策略都不会淘汰它。

### 命中率经济学

前缀缓存命中率因流量而异。命中率取决于：

1. **前缀长度分布**：共享前缀越长，每个请求中可缓存的比例越高。2,000 token 系统提示配合 100 token 用户查询，可缓存比例 95%；配合 10,000 token 用户查询则只有 17%。

2. **请求到达模式**：相同前缀的请求必须在缓存淘汰窗口内到达。单一主导系统提示的高 QPS 服务命中率接近 100%。多个不同系统提示的低 QPS 服务命中率接近 0%。

3. **缓存大小相对于工作集**：若活跃前缀工作集能放入 GPU HBM，命中率高。若工作集超过 HBM，命中率下降至工作集中 HBM 能容纳的比例。

**有效命中率**（从缓存服务而非重新计算的 prefill token 比例）是比请求级命中率更好的指标：

```
有效命中率 = 缓存服务的 token 数 / 总 prefill token 数
```

每个请求都有 2,000 token 共享前缀和 100 token 唯一后缀的工作负载，即使只有 50% 的请求缓存命中，有效命中率也达到 95%（另外 50% 重新计算前缀并为下一个请求填充缓存）。

### 多级缓存：GPU → CPU → 磁盘

GPU HBM（H100 80 GB）限制了前缀缓存工作集的总量。对于具有大量或多种不同系统提示的工作负载，工作集超出 HBM 范围。两种扩展方案：

**CPU DRAM 溢出：**
被淘汰的 KV cache block 移至 CPU DRAM（数百 GB）而非丢弃。在 GPU HBM 缓存缺失时，先检查 CPU DRAM，再重新计算。若找到，通过 PCIe 将 block 传回 GPU HBM。

传输成本：PCIe 4.0 带宽约 64 GB/s。1,000 token 前缀（16 字节/token/层 × 80 层 ≈ 1.28 MB）传输约 20 微秒——远比重新计算便宜（70B 规模 prefill 约需 5 毫秒）。几乎任何超过约 100 token 的前缀，重计算成本都远大于传输成本，CPU DRAM 都值得使用。

**磁盘（NVMe SSD）：**
第二级溢出层。NVMe 读取带宽约 7 GB/s，传输速度约为 PCIe DRAM 的 1/18。仅对访问频率极低的超长前缀（>10,000 tokens）有价值。3FS（[条目](../../deepseek/open-source-week/3fs/)）是专为高效服务大型 KV cache 工作负载构建的存储系统示例；Mooncake（[条目](../../moonshot/mooncake/)）的 KVCache 池将其扩展为解耦缓存存储。

### 与解耦 prefill/decode 的集成

在解耦服务（[DistServe 条目](./distserve/)、Mooncake）中，prefill 和 decode 在不同机器上运行。该架构下的前缀缓存增加了一个维度：**缓存存储在哪里，如何迁移？**

Mooncake 的设计：维护分布在所有 prefill 实例上的全局 KV cache 池。新请求到达时，将其路由到本地缓存中已有最长匹配前缀的 prefill 实例。这既避免了重新计算前缀，也避免了传输 KV cache——请求迁移到缓存，而非缓存迁移到请求。

路由问题（给定分布式前缀缓存，将请求发送到哪个 prefill 实例）成为关键系统问题：基于前缀哈希的一致性哈希将相似请求映射到相同 prefill 实例，提升本地命中率。这等价于"缓存感知的负载均衡"。

## 工程权衡

| 决策 | 得到什么 | 放弃什么 |
|---|---|---|
| 基于哈希的匹配（vLLM APC） | 简单；O(1) 查找；无树维护 | 仅精确匹配；不暴露前缀共享拓扑；淘汰不感知共同祖先 |
| 基数字典树匹配（SGLang） | 最长前缀匹配；自然共享拓扑；高效子树淘汰 | 树维护开销；实现稍复杂 |
| LRU 淘汰 | 简单；近因主导工作负载下接近最优 | 偶发的大前缀会挤出其他 block；新提示存在冷启动惩罚 |
| CPU DRAM 溢出层 | 有效缓存容量扩大 4–8 倍 | PCIe 传输延迟（约 20 μs/MB）；CPU 内存总线竞争；需要预取逻辑以隐藏延迟 |
| block 大小 16 tokens | 部分 block 浪费少；细粒度共享 | 16 token 对齐要求；小 block 意味着更多哈希表条目和更多指针追踪 |
| block 大小 64 tokens | 哈希条目更少；DRAM 局部性更好 | 前缀边界处不完整 block 的浪费更多；共享粒度更粗 |
| 解耦前缀缓存（Mooncake） | 实例间共享缓存；全局最优命中率 | 远程实例命中时的网络传输成本；路由复杂度 |

## 实验与结果

**vLLM APC 在共享系统提示工作负载上：**
- 512 token 系统提示配合短用户查询（约 50 tokens），高 QPS 下 APC 使 TTFT 降低约 60%（prefill 是 TTFT 瓶颈；缓存命中消除它）。
- 单一系统提示部署的暖缓存有效命中率 95% 以上。

**SGLang RadixAttention 在 Agent 工作负载上：**
- 在具有分支结构的多 call LLM 程序（思维树、工具调用链）上：与无前缀共享的 vLLM 时代（2023）基线相比，吞吐提升 5 倍。
- 命中率高度依赖程序结构；从一个根节点出发的宽浅树（多个并行分支）对共享根的有效命中率接近 100%。

**Mooncake（Moonshot 生产环境，2024）：**
- 带分布式前缀缓存池的 KVCache 中心解耦服务。
- 报告在 prefill 机队中生产环境 KV cache 命中率为 75%，相比无缓存方案 prefill 算力减少约 3 倍。

**CPU DRAM 层（vLLM 社区实证）：**
- 对于有超过 10 个不同系统提示（每个约 2,000 tokens）的工作负载，CPU DRAM 层将有效命中率从约 30%（仅 HBM）提升至约 85%（HBM + CPU DRAM），TTFT 相当——PCIe 传输足够快，与重计算相比几乎不可察觉。

## 可复现性说明

- **vLLM APC**：vLLM >= 0.4.0 中默认启用。旧版本通过 `--enable-prefix-caching` 开启。block 大小可通过 `--block-size` 配置。
- **SGLang RadixAttention**：默认启用。基数树淘汰和 LRU 策略代码位于 `sglang/srt/mem_cache/radix_cache.py`。
- **衡量命中率**：vLLM 在请求指标中暴露 `num_cached_tokens`；SGLang 为每个请求记录缓存命中统计。仪表化这些指标是理解工作负载是否受益的第一步。
- **针对缓存优化**：将提示结构化使共享前缀在前、唯一内容在后。提示起始处哪怕一个 token 的差异都会导致完全缓存缺失。某些框架提供显式的"前缀封装"API 以保证 block 对齐。
- **CPU 卸载**：vLLM >= 0.6 支持 `--cpu-offload-gb` 用于 CPU DRAM 前缀缓存。预取启发式（缺失时获取 vs 根据访问模式预取）显著影响延迟——生产部署可受益于针对 QPS 调整预取激进程度。

## 评注

前缀缓存是 LLM 服务中最直接有利的优化：它利用真实流量中已有的结构（重复的系统提示、few-shot 示例、RAG 上下文）来降低真实成本（prefill 计算）。与投机解码（需要调整草稿模型）或量化（需要精度验证）不同，前缀缓存是无损的，不需要任何模型改动。

实际收益上限取决于工作负载。对于单一系统提示的聊天机器人部署，暖缓存提供接近 100% 的命中率，系统提示的 prefill 实际上免费。对于多样化工作负载（每个请求都有唯一的大上下文），前缀缓存收益为零。ROI 分析很简单：测量流量的有效命中率；若低于 30%，进一步调优并不值得。

两个容易被低估的交互：

**前缀缓存 + 分块 prefill = block 补全。** 没有分块 prefill 时，提示不与 block 边界对齐的请求会产生一个既未缓存也无法被下一个请求缓存的不完整 block。分块 prefill 通过用 decode token 或下一个请求的前缀 token 填满该 block 来完成它，使其可被缓存。这就是为什么同时启用两者始终优于单独启用任何一个。

**前缀缓存 + 解耦 = 路由问题。** 在解耦机队（Mooncake、带多个 prefill 节点的 DistServe）中，某个 prefill 节点的缓存缺失可能是另一个节点的命中。朴素的轮询负载均衡会破坏有效命中率。需要缓存感知路由（基于前缀哈希的一致性哈希，或集中式缓存目录）才能达到理论命中率。这是一个定义明确的分布式系统问题，但在继承负载均衡器轮询的部署中往往被忽视。
