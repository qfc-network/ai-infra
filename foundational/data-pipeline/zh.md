# 数据管线：FineWeb、MinHash 与质量过滤

- **作者 / 机构**：Penedo 等（HuggingFace） · Wenzek 等（Facebook AI） · Soldaini 等（AllenAI） · Together AI
- **发表时间**：FineWeb: 2024（arXiv:2406.17557）· CCNet: 2020（LREC）· Dolma: 2024（ACL）· RedPajama-v2: 2023（GitHub）
- **链接**：[FineWeb 论文](https://arxiv.org/abs/2406.17557) · [FineWeb 数据集](https://huggingface.co/datasets/HuggingFaceFW/fineweb) · [CCNet](https://github.com/facebookresearch/cc_net) · [Dolma](https://github.com/allenai/dolma) · [RedPajama-v2](https://github.com/togethercomputer/RedPajama-Data)

## 一句话总结

训练数据质量是决定大模型能力的一阶因素——在固定算力预算下，其重要性甚至超过架构选择。从 Common Crawl 中构建高质量预训练语料需要多阶段管线：HTML 到文本提取、语言识别、URL 与启发式质量过滤、基于 MinHash 局部敏感哈希的近重复去重，以及学习型质量分类器。FineWeb 从 96 个 Common Crawl 快照中提取了 15 万亿 token，并证明精心调校的质量分类器优于基于困惑度的过滤方案。数据混合比例——网页、代码、书籍、数学、科学数据的占比——本身是一个训练超参数，通过小规模规模律实验在正式训练前完成调优。

## 背景与动机

### Common Crawl：金矿还是下水道

Common Crawl 是一个非营利组织，自 2008 年起持续抓取公开网页，每月快照以 WARC（Web ARChive）格式存档约 30–50 亿个页面。整个档案库压缩后超过 1 PB。它几乎是所有大规模大模型预训练语料的主要来源。

问题在于：原始抓取数据中充斥着低质量内容——垃圾邮件、搜索引擎优化（SEO）农场文章、导航菜单样板文字、成人内容、相互抓取的重复页面、机器翻译文本，以及有害或法律风险内容。在未过滤的 Common Crawl 上训练出的模型，其能力明显劣于在精选数据上训练的模型。工程挑战是以万亿 token 的规模，从中提取出足够高的信噪比。

### 为何数据质量影响算力效率

以 6 FLOPs/token 估算，在 1.4 万亿 token 上训练 700 亿参数模型的计算量约为：

```
6 × 70×10⁹ × 1.4×10¹² ≈ 5.9 × 10²³ FLOPs
```

这大约相当于 5000 个 A100 GPU 小时（峰值利用率），云端定价约 500 万美元。训练只能进行一次或少数几次。如果数据中有 10% 的近重复内容，或 20% 的文档是低质量 SEO 垃圾，这些浪费的算力无法追回。数据管线质量直接乘进了训练效率。

## Common Crawl 处理管线

### 第一阶段：WARC 转文本提取

原始 WARC 文件包含 HTTP 头部、原始 HTML 和二进制资源。第一步是从 HTML 中提取干净的文本。两种常用工具：

- **trafilatura**：Python 库；偏重精确率（提取正文内容，去除导航栏和广告）；适合新闻和文章内容。
- **resiliparse**（CCNet / FineWeb 使用）：更快，召回率更高；用于高吞吐量管线。

提取质量影响显著。导航菜单、Cookie 横幅、广告文字、评论区等若渗漏进来，就会成为训练数据。FineWeb 结合 resiliparse 进行提取，并辅以自定义后处理规则去除残余 HTML 痕迹。

### 第二阶段：语言识别

使用 `fastText` 语言识别模型（具体为 Meta 在 Wikipedia/Tatoeba 上训练的 `lid.176.bin`），对每篇文档的约 200 个字符样本进行语言分类。处理速度：单 CPU 核心约每秒 20 万篇文档。

FineWeb 目标为英语，保留英语置信度 ≥ 0.65 的文档。对于多语言语料库（mC4、ROOTS、CulturaX），语言识别阈值按语种分别应用，结果按语种分片存储。

### 第三阶段：URL 与启发式预过滤

在进行开销较大的逐文档处理之前，廉价的基于 URL 的过滤器先剔除已知低质量来源：

- 成人内容域名黑名单（UT1、NSFW 域名列表）。
- 与垃圾农场相关的 URL 模式（大量数字路径、域名生成算法特征）。
- `.onion` 地址、有问题的 `.gov`/`.edu` 子域名。

随后进行逐文档启发式过滤（参考 C4 和 MassiveText 的方案）：

- **文档长度**：提取后至少 200 个字符。
- **行长度分布**：行长中位数 > 30 个字符（过滤导航链接密集页面）。
- **字母数字字符比例**：≥ 70% 的字符为字母数字或常见标点。
- **以标点结尾的行比例**：≥ 80% 的行以 `.`、`?`、`!`、`:`、`"` 结尾——过滤关键词列表和要点堆砌式垃圾。
- **符号与词语比率**：过滤含有过多 `#`、`{`、`|`、`\` 字符的页面。
- **重复内容**：过滤任意行出现 ≥ 10 次的页面（页眉 / 页脚检测）。

### 第四阶段：MinHash 去重

启发式过滤能去除明显垃圾，但无法处理近重复内容：同一篇文章被 500 个新闻聚合器转发、产品描述从厂商网站抓取、样板法律免责声明、维基百科镜像等。近重复内容会造成记忆化压力，并可能在训练语料中主导某些话题的分布。

**MinHash 去重**是规模化处理近重复的标准方案。算法流程：

1. 将每篇文档分词为 n-gram 集合（通常为 5-gram）。
2. 对 K 个独立哈希函数中的每一个 h_k，计算文档中所有 n-gram 的最小哈希值。这个 K 维向量即为该文档的 **MinHash 签名**。
3. 内容相似的文档签名也相似——具体而言：

**核心公式——MinHash Jaccard 估计：**

```
Pr[min_{h}(A) = min_{h}(B)] = |A ∩ B| / |A ∪ B| = Jaccard(A, B)
```

两篇文档在随机哈希函数下最小哈希值相同的概率，等于它们在 n-gram 集合上的 Jaccard 相似度。使用 K=128 个哈希函数时，估计的标准差约为 1/√128 ≈ 0.09。

4. 使用**局部敏感哈希（LSH）**将文档分组到桶中：将 K 维签名分成 B 个各含 R 行的波段；若两篇文档在至少一个波段完全相同，则为候选近重复对。这产生阈值效应：Jaccard ≥ 0.8 时几乎所有相似对都成为候选；Jaccard < 0.7 时几乎没有。

5. 对每个桶中的文档形成连通分量，保留一个代表文档。不足约 200 个 token 的文档排除在去重之外（短文本会产生误匹配）。

**计算开销**：对 15 万亿 token 进行 MinHash 去重需要处理约 1000 亿篇文档。瓶颈在于 LSH 匹配步骤，通过 Spark 或 Ray 集群并行化处理。FineWeb 报告完整去重过程的云端费用约 10 万美元。

### 第五阶段：质量过滤

去重后，剩余语料中仍存在大量低质量内容。主要有两类方案：

**启发式规则（C4 风格）**：基于对 Common Crawl 质量的人工检查制定规则。FineWeb 应用了 30 余条规则，包括检测 lorem ipsum 占位文本、过多非 UTF-8 码点、提取后极短文档，以及行大量为 URL 的文档。

**分类器质量过滤**：训练一个二元文本分类器：
- 正例：精选高质量文本（维基百科、wikiHow、高质量新闻、书籍）。
- 负例：启发式过滤后的 Common Crawl 随机样本。

分类器为每篇文档打出 [0,1] 的质量分数，高于阈值（通常为 0.5）的文档被保留。

**FineWeb 的关键发现**：在以 1.4B 模型、3500 亿 token 训练的消融实验中，质量分类器明显优于基于困惑度的过滤方案（KenLM）。分类器过滤的数据在 MMLU、HellaSwag 和 ARC 等下游基准上均产生更好的结果。

**困惑度过滤（KenLM）**：另一种方案：在高质量文本（维基百科）上训练 n-gram 语言模型，保留困惑度低于阈值的文档。速度快、无需标注。局限：困惑度过滤倾向于偏好正式、百科全书式风格，可能过度删除有效的非正式文本或专业领域内容。

## 数据混合与课程安排

### 混合比例这一超参数

现代预训练语料通常混合多个具有不同特征的数据源：

| 来源 | 典型占比 | 质量特点 |
|---|---|---|
| 网页（过滤后 Common Crawl） | 60–80% | 广度大；噪声风险高 |
| 代码（GitHub、StackOverflow） | 5–15% | 高密度推理模式 |
| 书籍 / 长文本 | 5–10% | 长程连贯性好 |
| 科学论文（arXiv、S2ORC） | 2–5% | 技术精确性高 |
| 数学（MATH、AoPS、教材） | 1–5% | 结构化推理 |
| 精选问答、维基百科 | 2–5% | 事实准确性高 |

各来源的比例是影响下游能力的超参数，且影响方式并不直观。代码比例高的混合提升推理能力和结构化输出。数学比例高的混合提升算术和逻辑任务。正确的平衡点取决于目标应用场景。

### 用规模律消融实验选定混合比例

由于 700 亿参数训练无法轻易重复，数据混合决策通过**规模律代理实验**完成：用不同混合比例分别训练多个 10 亿参数模型，在 200 亿 token 上训练，测量下游基准，拟合规模曲线，将最优混合比例外推到 700 亿参数规模。

Llama 3、DeepSeek 等生产级模型均采用这种方式调优。背后的假设是：最优混合比例在规模上大致不变——在 10 亿参数下表现好的混合，在 700 亿下同样表现好。这一假设并不完美，但在实践中是必要的。

### 课程顺序安排

训练内数据的排列顺序影响收敛效果。常见策略：
- **均匀随机打乱**：基线方案；防止模型在近期见到重复数据。
- **质量递进排列**：训练前期用低质量数据，后期用高质量数据。直觉上，模型先从大量噪声数据中学习基础模式，再在高质量数据上细化。
- **训练末期针对特定能力的上采样**：Llama 3 在训练最后 10% 阶段对数学和代码数据进行上采样，以提升推理能力，同时不影响其他部分的训练效果。

## 工程权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| 仅启发式质量过滤 | 速度快；可解释；无需训练 | 可能系统性地删除有效内容；规则需按语言 / 领域人工维护 |
| 基于分类器的质量过滤 | 下游模型质量更好；适应内容分布 | 需要标注数据；分类器质量取决于"高质量"的定义；可能放大偏见 |
| 激进的 MinHash 去重（Jaccard ≥ 0.8） | 去除近重复；减少记忆化；平衡主题过度表达 | 可能删除合法重复内容（如代码中的标准许可证头）；略微减少语料规模 |
| 困惑度过滤（KenLM） | 简单；快速；无需标注 | 偏向正式 / 百科全书式文本；损害非正式或技术领域的覆盖范围 |
| 更大的 CC 快照覆盖范围 | 数据更多；时间覆盖更广；每篇文档的重复更少 | 收益递减；旧快照质量更差；处理成本线性增长 |
| 特定领域数据上采样（代码、数学） | 显著提升目标能力 | 改变分布；若力度过大可能损害未上采样领域的性能 |

## 实验结果

**FineWeb（Penedo 等，2024）**：从 96 个 Common Crawl 快照（2013–2024）中提取 15 万亿 token。所有管线阶段后，FineWeb 保留了约 2–3% 的原始抓取量。质量分类器过滤产生了 FineWeb-Edu 子集（教育类内容），在知识密集型基准上优于完整 FineWeb 数据集，尽管规模更小（1.3 万亿 token）。在 FineWeb-Edu 上用 3500 亿 token 训练的 14 亿参数模型，在 MMLU 上达到了 GPT-3.5 级别的性能。

**CCNet（Wenzek 等，2020）**：引入了 fastText 语言识别 + KenLM 困惑度过滤的逐语言管线。证明与未过滤的 Common Crawl 相比，困惑度过滤使单语言 LM 的下游任务性能大约提升三倍。

**Dolma（AllenAI，2024）**：用于训练 OLMo 的 3 万亿 token 语料。多来源混合：Common Crawl（67%）、C4、GitHub、书籍、科学论文、维基百科。完整管线代码和数据来源均公开记录，支持可复现性。

**RedPajama-v2（2023）**：来自 84 个 Common Crawl 快照的 30 万亿+ token，并为每篇文档存储了计算好的质量信号（MinHash、困惑度、分类器得分），允许下游用户应用自定义过滤阈值，无需重新运行整个管线。

## 综合评述

数据管线工程是大模型开发中最不引人注目的环节，也可能是影响最深远的。在精心策划的 1 万亿 token 数据集上训练的模型，往往优于同等架构在 5 万亿 token 低质量过滤网页数据上训练的结果。那些看似预处理日常事务的过滤阶段——语言识别、启发式规则、去重、质量分类器——共同决定了模型权重是在编码有用的世界知识，还是在记忆垃圾邮件和重复样板文字。

MinHash 去重步骤值得更多重视。训练数据中的近重复文本带来两个不同问题：其一，模型更容易记忆高频出现的内容（包括法律免责声明、SEO 优化文章结构等不良内容）；其二，扭曲训练期间接触的话题有效分布——一条被 1 万个转发站点覆盖的新闻事件，对模型来说"重要性"是只被报道一次的同等事件的 1 万倍。Jaccard ≥ 0.8 的激进去重能同时解决这两个问题。

数据混合决策是[规模律（Chinchilla）](../scaling-laws/zh.md)中的机制发挥实际工具价值的地方。你无法为了找到最优混合比例而多次训练 700 亿参数模型，因此需要在 10 亿参数规模代理搜索，并信任规模不变性大致成立。这并不完美——某些能力（如长上下文推理）在 10 亿参数规模下表现不足——但这是目前最好的近似方案。规模律指导的计算最优规模设定与经验性的混合比例选择相结合，定义了当前预训练语料构建的最先进水平。另见 [DeepSeek V3](../../deepseek/v3-tech-report/zh.md) 和 [Llama 3](../../meta/llama3/zh.md)，了解大规模生产训练如何落地这些原则。
