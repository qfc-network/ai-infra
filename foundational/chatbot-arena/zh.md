# Chatbot Arena 与成对评测

- **平台**：Chatbot Arena（LMSYS Org）
- **创建方**：LMSYS（大型模型系统组织）—— UC Berkeley、UCSD、CMU
- **链接**：[Arena](https://chat.lmsys.org) · [论文 arXiv:2403.04132](https://arxiv.org/abs/2403.04132) · [FastChat GitHub](https://github.com/lm-sys/FastChat)

## 一句话总结

Chatbot Arena 是一个实时平台，用户在此与两个匿名 LLM 同时对话，并投票选出响应更好的一方。截至 2024 年中，平台已积累超过 100 万条人类偏好投票，涵盖 100 余个模型——这是目前最大的公开 LLM 人类偏好数据集。平台使用基于这些成对比较结果拟合的自举 Bradley-Terry 模型对模型进行排名。它的诞生源于静态基准的饱和：到 2024 年，MMLU 顶尖分数已突破 90%，基准污染使排名失去可信度。Arena 提供了一种静态基准无法复制的信号：针对多样化、新颖提示词的真实人类偏好，而这些提示词天然无法被预先污染。对基础设施团队而言，Arena Elo 已成为驱动实验室模型选型决策的生产质量信号，采集的偏好数据也通过 DPO 和 RLHF 直接反哺后训练流水线。

## 为何静态基准走向饱和

Open LLM Leaderboard 时代（大致为 2022–2024 年）揭示了静态基准的根本性上限问题。

到 2024 年初，领先模型在 MMLU 上的分数已达 85–90% 以上。在前沿水准上，2 分的 MMLU 差异意味着什么实际上并不清晰：剩余错误集中在最难的题目上，人类评估者往往会认为"更低"分数模型的响应实际上更有用。序数排名正在失去意义。

与此同时，污染问题急剧恶化。基于更大范围互联网爬取数据训练的模型，越来越多地在训练过程中摄入了被复制到学习指南、作业辅导网站和基准分析博客中的 MMLU 题目。测试题目不再因为"私有"而得到保护——它们已经公开且被广泛传播。社区开发了 n-gram 重叠检测方法，但改写形式的污染仍然无从检测。

更深层的问题在于多项选择准确率与对话质量的相关性很弱。一个在 MMLU 上表现优化的模型——记住了大量学术事实——在遵循复杂指令、保持对话连贯性或编写可用代码方面可能要差得多。而这些恰恰是产品用户真正关心的任务，MMLU、HellaSwag 或 ARC 均未对其进行测试。

Chatbot Arena 的设计初衷正是填补这一空白：一个无法被污染、由目标最终用户评测、针对用户真实需求任务的基准。

## 平台架构与数据采集

Arena 并排呈现两个对话界面，分别连接不同的模型，但在用户投票前模型身份保持隐藏。这种盲测设置避免了"品牌偏好"偏差——即用户无论实际响应质量如何都投票给 GPT-4 的情况。

用户流程：
1. 用户提交消息，两个模型收到相同的提示词。
2. 两个响应同时显示。
3. 用户投票：A 更好、B 更好，或平局（含细分：都好/都不好）。
4. 模型身份揭晓。
5. 投票以（模型A、模型B、结果）三元组的形式记录。

会话支持多轮对话。每一轮都延伸了比较上下文；用户可在任意一轮投票。这测试的是多轮连贯性，而不仅仅是单次响应质量。

规模：截至 2024 年中，平台已记录超过 100 万条投票。在这一规模下，Elo 评分的置信区间（约 ±15 分）已经足够紧，可以检测出模型间有意义的差异。新模型大约需要 2,000–3,000 场对战才能获得稳定的 Elo 估计，按 Arena 的流量水平，视模型曝光度不同需要数天到数周。

LMSYS 将服务基础设施以 **FastChat** 的形式开源——一个处理匿名会话路由、模型身份隐藏和投票记录的多模型服务框架。FastChat 支持兼容 OpenAI 的 API，可轻松将流量路由至任意后端（vLLM、HuggingFace TGI 或私有 API 端点）。

## Bradley-Terry 模型与 Elo 评分

Arena 的排名系统基于 **Bradley-Terry 模型**——成对比较问题的标准统计框架。

该模型假定每个参赛者具有一个潜在强度参数，模型 A 击败模型 B 的概率为：

```
P(A beats B) = exp(β_A) / (exp(β_A) + exp(β_B))
```

给定一组观测到的对战结果，通过最大似然估计 β 参数：找到使所有观测到的胜负结果对数似然最大的 β 值。这等价于以两个模型 ID 的独热编码为特征、以二元结果为标签的逻辑回归。

关键性质：Bradley-Terry 具有传递性。若 A 胜 B 且 B 胜 C，模型便能推断 A 很可能胜 C，并给出量化估计。这使得即便大多数模型对从未直接对战，也能从成对对战中对 100 余个模型进行排名。

**Elo 评分系统**（从国际象棋中借鉴）是同一思想的在线近似：

```
expected_score(A vs B) = 1 / (1 + 10^((rating_B - rating_A) / 400))
delta_Elo = K * (actual_score - expected_score)
```

其中 `actual_score` 胜为 1、平为 0.5、负为 0，`K = 32` 为更新步长。

Arena 并不使用实时 Elo 更新（对战处理顺序会影响结果），而是定期用最大似然法对所有累积投票重新拟合完整的 Bradley-Terry 模型。置信区间通过**自举重采样**估计：随机抽取 80% 的投票，重新拟合 Bradley-Terry，重复 1,000 次，以所得 β 分数的第 5–95 百分位数作为置信区间。这一自举流程比解析式 Elo 方差估计更稳健，因为它考虑了各模型对之间对战分布不均匀的情况。

## MT-Bench：自动化多轮评测

在将模型部署到实时 Arena 之前，LMSYS 使用 **MT-Bench** 进行快速自动化筛选。

MT-Bench 由 80 个高质量多轮对话组成，横跨 8 个类别：写作、角色扮演、推理、数学、代码、信息抽取、STEM 知识和人文学科。每段对话有两轮；第二轮要求模型在第一轮响应的基础上继续作答。GPT-4 担任评委，对每个响应打 1–10 分。

MT-Bench 不等于 Arena：它是自动化的，使用 GPT-4 作为人类偏好的代理，基于固定提示词集运行。但它提供了与 Arena Elo 相关性尚可的快速信号，对于在决定将模型部署到费时费力的实时 Arena 之前筛选模型很有价值。

在前沿水准，MT-Bench 分数与 Arena Elo 的相关性会失效：在 GPT-4、Claude 3 Opus 和 Gemini Ultra 之间，MT-Bench 分数高度集中，而 Arena Elo 存在实质差异。在这个水准，人类评估者能够在文体打磨、推理深度、指令遵循等维度上区分模型质量，而 GPT-4 评判会漏掉这些差异。

## LLM 即评委的基础设施

当人类投票太慢或太贵时，Arena 式大规模成对比较需要自动化评判。LLM 即评委的模式使用一个高能力模型（GPT-4、Claude 3 Opus）来评估成对比较。

提示词结构：

```
System: 你是一位公正客观的评委，正在评估两个 AI 助手。
        给定用户问题和两个响应，判断哪个响应更好，或它们是否平局。

User: [问题]
{用户问题}

[响应 A]
{响应_A}

[响应 B]
{响应_B}

评估两个响应，考量：准确性、有用性、清晰度、安全性。
以如下格式输出你的判断：[[A]]、[[B]] 或 [[C]]（平局）。
```

两种系统性偏差需要缓解：

**位置偏差**：LLM 评委倾向于偏好排在前面的响应。缓解方案：对每对比较运行两次，交换 A 和 B 的位置。若两次结果一致，记录该结果。若不一致（AB 说 A 赢，BA 说 B 赢），记为平局或提高人工审核权重。

**冗长偏差**：LLM 评委倾向于给更长的响应打更高分，与实际质量无关。这与人类用户的偏好相反（用户更喜欢简洁准确的响应而非冗长的）。没有干净的缓解方案——了解这一偏差并在评分标准中明确惩罚冗长能在边际上有所帮助。

自动化评判的成本：GPT-4 按 $30/百万输出 token 计算，评判 10 万对对战（每对两次评估，每次约 500 token）约花费 3,000 美元。按 Arena 规模（数月积累 100 万场对战），对所有对战进行自动化评判将花费约 3 万美元——对有充足资金的研究团队可行，但对个人研究者不现实。

## Chatbot Arena Hard

完整 Arena 提示词分布中包含许多简单提示词，在这些提示词上强模型总是达成共识。为了对前沿模型比较获得更具判别力的信号，LMSYS 维护了 **Chatbot Arena Hard**：一个约 500 条提示词的筛选子集，在这些提示词上顶级模型分歧最大。

选择标准：顶级模型（GPT-4、Claude、Gemini）之间人类投票分歧最大的提示词。这些提示词往往涉及复杂推理、细致的创意写作、多约束任务或指令遵循的边缘案例——恰好是区分前沿模型的任务。

相比完整分布，使用 Arena Hard 作为基准每条提示词的统计判别能力提升 3–5 倍，因为集合中的每条提示词都足够难，模型能力而非噪声决定了结果。

## 向后训练的反馈闭环

Arena 最重要的基础设施影响不是评测本身，而是它为后训练生成的数据。

每场 Arena 对战产生一个（提示词、响应A、响应B、偏好）四元组，其中偏好是真实人类对自然语言的判断。这正是以下任务所需的数据格式：

- **RLHF 奖励模型训练**（见 `../rlhf/`）：奖励模型从（提示词、响应）对上的成对人类偏好中学习
- **DPO 训练**（见 `../dpo/`）：DPO 直接消费（提示词、选中响应、拒绝响应）三元组，其中选中和拒绝来自 Arena 投票结果

Arena 公开发布的偏好数据（基于研究许可）使外部实验室无需自行运营人类偏好采集流水线即可引导后训练流程。Alpaca Farm、UltraFeedback 和 OpenPreferences 等数据集均借鉴或受到 Arena 式采集方式的启发。

反馈闭环时延：一个模型部署到 Arena，两周内积累 5,000 场对战，生成 5,000 条偏好对，随即混入下一次针对 Arena 投票揭示的弱点的后训练运行。对于紧密集成了评测与后训练流水线的实验室，这一闭环以周到月为时间尺度运转。

## 运营一个 Arena 的基础设施

部署一个有竞争力的评测平台需要：

**模型服务层**：以低延迟同时服务 100 余个模型。实践中，较小的模型（7B–13B）在共享 GPU 集群上运行；前沿模型（GPT-4、Claude）通过 API 访问。FastChat 的多后端架构处理这种异构性。会话亲和性确保用户的对话在整个对战过程中保持在同一个模型上。

**匿名化执行**：必须在投票前隐藏模型身份。这是一个具有真实工程后果的产品需求——任何模型标识符（响应延迟、格式风格、字符级行为）都可能向经验丰富的用户泄露身份。两个模型的响应流式传输必须同时开始，以防止基于时序的去匿名化。

**投票记录与去重**：每条投票是一条（会话ID、模型A_ID、模型B_ID、结果、时间戳）记录。去重过滤同一会话的重复投票。机器人检测防止自动投票刷分。

**Bradley-Terry 拟合流水线**：定期（每日或按需）对累积投票重新拟合完整 BT 模型。以 100 万条投票、100 余个模型为规模，逻辑回归在 CPU 上数秒内收敛；1,000 次迭代的自举重采样需要数分钟。

**结果发布**：带置信区间的 Elo 分数公开发布；个人对战日志在去除提示词中的个人信息后供研究使用。

## 工程权衡

| 评测方法 | 单数据点成本 | 速度 | 污染风险 | 人工 vs 自动 | 可复现性 |
|---|---|---|---|---|---|
| Chatbot Arena（实时人工） | 高（含服务约 $1–5/票） | 需数周达到稳定排名 | 无（新颖提示词） | 人工 | 低（提示词分布随时间变化） |
| MT-Bench（LLM 即评委） | 低（约 $0.05/题） | 数分钟 | 中等（固定提示词） | 自动 | 高（固定提示词集） |
| lm-eval-harness（MMLU 等） | 极低（约 $0.001/题） | 数小时 | 高（静态公开测试集） | 自动 | 极高 |
| 内部红队测试 | 极高（专家人工成本） | 数天 | 无 | 人工专家 | 低（覆盖范围因人而异） |
| 生产流量 A/B 测试 | 边际成本近零 | 数周 | 无 | 隐式人工 | 中等（存在混淆因素） |

## 评论

Chatbot Arena 的持久贡献不在于任何特定的 Elo 排名——排名会随每个新模型不断变化。其真正的贡献在于确立了一个原则：**在产品层，人类偏好是 LLM 评测的正确目标**。多项选择准确率衡量的是知识记忆；MT-Bench 和 LLM 即评委衡量的是质量的代理；而 Arena 衡量的是事物本身。

这对基础设施投资具有直接影响。每个严肃对待 LLM 的实验室现在都维护着某种形式的实时偏好采集，即便不对外公开。采集到的数据比它产生的模型排名更有价值——来自真实用户对话、真实用户任务的偏好对，比任何人工构建的数据集都更适合用于后训练，因为它们捕捉了用户在实际使用中遇到的准确失败模式。

Arena 的弱点与其优势恰好相反：它慢、贵，且难以复现。单次评测需要数周流量积累；提示词分布反映的是实际使用平台的用户（以英语为母语的技术倾向用户），而非完整的部署场景范围。对于专门领域（医疗、法律、代码）的生产模型选型，领域专用内部 Arena 比公开的 LMSYS 排名更有参考价值。
