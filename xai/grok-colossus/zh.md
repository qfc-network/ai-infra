# xAI Grok 模型系列与 Colossus 集群

- **机构**: xAI（Elon Musk）
- **关键时间节点**: Grok-1 开放权重发布于 2024 年 3 月；Colossus Phase 1 于 2024 年 10 月宣布；Grok-3 于 2025 年 2 月上线
- **相关链接**: [Grok-1 权重（HuggingFace）](https://huggingface.co/xai-org/grok-1) · [xAI API](https://api.x.ai) · [Colossus 公告](https://x.ai/blog/colossus)

## 概要

xAI 在约 122 天内，于田纳西州孟菲斯建成了一个拥有 10 万张 H100 的单一园区训练集群（Colossus Phase 1），这是截至当时公开宣布的规模最大的单地点 GPU 集群。该系统用于训练 xAI 的前沿推理模型 Grok-3。将所有算力集中于同一物理站点，是一个明确的基础设施赌注：消除同步分布式训练中跨数据中心的通信延迟——这是之前任何基于 H100 的多站点集群都未曾在此规模上尝试的。本文涵盖 Grok 模型系列的架构、Colossus 的建设过程、Grok-3 训练中的并行策略与存储决策，以及与 X（Twitter）平台深度集成所形成的推理需求模式。

## 1. Grok 模型系列

### Grok-1：首个前沿开放 MoE 模型

Grok-1 于 2024 年 3 月以 Apache 2.0 许可证开放权重发布，是一个**3140 亿参数的混合专家（MoE）变换器**，采用 8 个专家、top-2 路由机制。发布时，它是公开可用的最大开放权重模型，也是第一个在前沿规模下公开发布完整权重的 MoE 模型。

架构摘要：
- 总参数量 3140 亿；每个 token 激活约 860 亿参数（8 个专家中取 top-2）
- MoE 路由方式与 Mixtral 8x7B 在设计思路上相近，但规模大幅提升
- 上下文窗口为 128k token
- 采用旋转位置编码（RoPE）
- 训练超参数和数据集信息未公开

开放权重是一步战略举措：xAI 在开源 ML 社区中缺乏先前积累的声誉，在 Mixtral 刚刚证明稀疏 MoE 能以更低激活成本匹敌密集模型的时间节点上，发布 Grok-1 建立了技术可信度。

### Grok-1.5 与 Grok-2：迈向多模态

Grok-1.5（2024 年 4 月）和 Grok-2（2024 年 8 月）均以闭源方式发布。Grok-2 在标准评测榜单（MMMU、GPQA、HumanEval、MATH）上与 GPT-4o 竞争力相当，并引入了 **Aurora 图像理解模块**——一个与语言骨干融合的视觉编码器，支持图像描述、图表解读和视觉推理。Grok-2 的权重未对外发布，模型仅通过 xAI API 和 X 平台提供服务。

Grok-2 及后续版本的架构要点：
- Aurora 模块采用视觉变换器编码器，通过交叉注意力层与语言骨干融合，模式上类似 LLaVA 风格的视觉指令微调，但在预训练阶段即完成集成
- 多模态输入下上下文窗口保持 128k token
- 推理侧针对社交媒体查询量级进行亚秒级延迟优化

### Grok-3：在 Colossus 上训练

Grok-3 于 2025 年 2 月上线，发布时在推理能力评测榜单上声称达到行业最先进水平，完全在 Colossus Phase 2（20 万 H100 扩容后）上训练。xAI 表示其训练算力约为 Grok-2 的 10 倍。Grok-3 在编程、数学和科学任务上直接竞争 GPT-4o 和 Claude 3.5 Sonnet。同期还发布了针对低延迟场景优化的"Grok-3 mini"变体。

Grok-3 采用 FP8 训练——这到 2024–2025 年已成为前沿实验室的行业标准做法。FP8 前向传播配合 BF16 优化器状态，相比纯 BF16 在 H100 上提供约 2 倍的吞吐量提升。

## 2. Colossus Phase 1——10 万张 H100 单地点集群

### 建设时间线与规模

Colossus Phase 1 位于田纳西州孟菲斯。建设从 2024 年中期启动，据报道在约 **122 天**内达到运营状态——实现这一速度，采购、供电基础设施和机架安装必须并行推进而非顺序进行。xAI 于 2024 年 10 月正式宣布该集群。

硬件概况：

| 指标 | 数值 |
|---|---|
| GPU 型号 | H100 SXM5 |
| GPU 总数 | 100,000 |
| 每节点 GPU 数 | 8（NVLink 域） |
| 总节点数 | 约 12,500 |
| 节点内带宽 | NVLink 4.0，双向 900 GB/s |
| 节点间互连 | InfiniBand HDR/NDR，RDMA |
| 集群峰值功耗 | 约 200 MW |
| 存储规模 | 数十 PB，基于闪存的分布式存储 |
| 支持上下文窗口 | 128k token |

### 为何选择单地点？

将所有算力集中于同一物理园区的依据，根植于分布式训练中集合通信的物理规律。

全规约（AllReduce）、全聚合（AllGather）、规约分散（ReduceScatter）等集合操作的速度，受制于**拓扑中最慢链路的延迟**。对于 N 个 rank 的环形 AllReduce，每步时间正比于：

$$T_{\text{allreduce}} \approx 2 \cdot \frac{N-1}{N} \cdot \frac{M}{B} + 2(N-1) \cdot \alpha$$

其中 M 为消息大小，B 为对剖带宽，α 为每跳延迟。两个数据中心之间的广域网链路会引入 1–10 ms 的 α；而在单一园区内通过 InfiniBand 互连，α 低于 5 μs——相差三个数量级。对于一个在 10 万 GPU 上运行 10,000 次梯度步的训练任务，即使是 1 ms 的跨数据中心延迟惩罚，也会累计带来约 3 小时的无效等待时间。

多站点训练的缓解策略（梯度压缩、异步数据并行、分层 AllReduce）各自引入正确性或吞吐量代价。xAI 的判断是：通过单一物理站点彻底消除这一问题，优于在工程上持续管理它。

**与同期集群的规模对比：**

| 集群 | GPU 数量 | 部署形式 | 地点 | 代表性训练 |
|---|---|---|---|---|
| Colossus P1（xAI） | 100,000 张 H100 | 单一站点 | 孟菲斯 | Grok-3 |
| Meta（Llama 3 405B） | 约 16,000 张 H100 | 多集群 | 多站点 | Llama 3 405B |
| Google TPU v5p | 约 8,960 个 TPU | Pod | 多站点 | Gemini Ultra |
| Microsoft/OpenAI | 约 20,000 张 A100 | Azure | 多站点 | GPT-4（估算） |

Colossus P1 的 GPU 数量约为 Meta Llama 3 训练集群的 6 倍，且作为单一同步训练域运行，而非联邦式安排。

### 网络互连结构

每个节点内，8 张 H100 SXM5 GPU 通过 NVLink 网状拓扑互连，提供 900 GB/s 双向带宽。这一带宽足以支持节点内的张量并行（TP）：梯度和激活分片在 NVLink 域内交换，无需触及速度较慢的 InfiniBand 互连。

节点间通过 InfiniBand HDR（每端口 200 Gb/s）和 NDR（每端口 400 Gb/s）提供支持 RDMA 的互连结构，用于流水线并行（PP）和数据并行（DP）通信。在 12,500 个节点的规模下，交换结构需要采用多级胖树拓扑以维持全对剖带宽；xAI 尚未公开具体的互连结构细节。

### 存储系统

在前沿训练规模下，检查点和数据集 I/O 带来独立的存储需求：

- **检查点存储**：3140 亿参数模型以 BF16 表示，每个检查点约需 630 GB。加上 Adam 优化器状态（每个参数额外两个 BF16 张量），完整优化器检查点约为 2.5 TB。在 10 万 GPU 规模下，每 500 训练步保存一次检查点（保守间隔），存储写入带宽和 IOPS 是一流约束，而非次要问题。基于闪存的分布式存储（NVMe over RDMA）是避免检查点成为训练瓶颈的必要条件。
- **数据集 I/O**：预分词数据集顺序读取；每 GPU 带宽需求相对适中（约 500 MB/s 聚合带宽），但需持续数周。

## 3. Colossus Phase 2——目标 20 万张 H100

Phase 2 随 Grok-3 训练一同宣布，将孟菲斯园区扩展至 20 万张 H100，峰值功耗翻倍至约 **400 MW**。这一规模相当于一个小型城市的供电需求。

### 供电与散热挑战

在 400 MW 规模下，集群的功耗需求超出了商业电网在单建筑密度下能可靠供给的范围。xAI 通过以下方式应对：

- **现场发电**：部署燃气轮机或辅助发电设备，提供超出公共电网的专用容量。在美国市场，电网接入排队周期长达 3–5 年，现场发电是规划超过 100 MW 集群的前提条件。
- **机架级直接液冷（DLC）**：H100 SXM5 节点每张 GPU 热耗约 700W，每个 8-GPU 节点约 5.6 kW。在 25,000 个节点的规模下，气冷方式在每机架超过 30–40 kW 后变得物理上不可行；DLC 允许机架密度达到 60–100 kW。背门式热交换器或直接接触式冷板均在 Colossus 规模下得到部署。

### GPU 采购

在 2024–2025 年的供应紧张环境下，额外采购 10 万张 H100 面临 NVIDIA 的配额管控：H100 SXM5 的分配实际上只面向优先级最高的超大规模云和政府客户。xAI 与 NVIDIA 的关系——以及 Elon Musk 的个人影响力——是建设时间表得以实现的竞争性投入。常规采购渠道无法支撑这一速度。

## 4. Grok-3 的训练基础设施决策

### 选择 H100 而非 H200 或 Blackwell

选择基于 H100 SXM5 而非等待 H200 或 Blackwell（B100/B200），本质上是一个时间窗口决策：

- H100 SXM5 在 2024 年中期可批量供货
- H200（采用 HBM3e，内存带宽相比 H100 提升约 1.4 倍）从 2024 年中期开始小批量出货，但在 Phase 1 所需的时间节点内无法做到 10 万级规模供货
- B100/B200 Blackwell 因掩模版修订延期至 2025 年；若等待 Blackwell，训练窗口将推迟 12 个月以上

等待下一代硬件的代价，实质上是将 Grok-3 的训练窗口拱手相让给竞争对手。按时建成的 H100 集群所提供的聚合算力，优于一个建设更晚但采用更新架构的较小集群。

### 四维并行策略

对于一个在 10 万 GPU 上训练 3140 亿以上参数 MoE 模型的任务，并行分解方式受拓扑和显存的双重约束：

- **张量并行（TP=8）**：在 NVLink 域内进行。将注意力头和 FFN 的行/列分片到 8 张 GPU 上。NVLink 带宽（900 GB/s）足以支撑每个变换器层的 AllGather 和 ReduceScatter 操作。
- **流水线并行（PP）**：通过 InfiniBand 跨节点进行。微批次处理摊平了流水线气泡。在 126 层以上的模型中，PP=8 或 PP=16 使每个 stage 的显存占用处于可控范围。
- **数据并行（DP）**：跨流水线副本组进行。在 TP=8、PP=16 的条件下使用 10 万 GPU，DP 维度约为 781——即每步执行梯度规约的独立副本数量。
- **专家并行（EP）**：在 MoE 层中，8 个专家分布在各 EP rank 上。专家调度（将 token 路由到对应专家 GPU）引入了密集模型中没有的全对全通信，这是 MoE 训练特有的主要额外开销。

FP8 训练同时降低了显存压力（在精度允许的层存储 FP8 激活值）和计算压力（H100 的 FP8 Tensor Core 吞吐量约为 BF16 的两倍）。

### 规模化检查点的存储开销

在 10 万 GPU 加优化器状态的条件下：

- 单次检查点写入量：约 2.5 TB 优化器状态 + 约 630 GB 模型权重 = 约 3.2 TB
- 按聚合写入带宽 10 GB/s（闪存分布式存储）：每个检查点约需 5 分钟
- 在 500 步的检查点间隔下，若所有 GPU 同时并行写入，检查点操作约消耗约 1% 的训练时间——这是可接受的，但前提是所有 GPU 能同步并行写入

在 10 万 GPU 规模下，任意单张 GPU 发生硬件故障的估计平均时间为每隔数小时便会出现一次，这使得频繁检查点成为不可或缺的操作。存储系统必须能够在不节流训练的前提下承受检查点 I/O 压力。

## 5. 推理基础设施

### 训练与推理双用集群

Colossus 以双用模式运行：模型开发阶段承担训练任务；在训练轮次之间或并行期间，集群转为 X 平台和 xAI API 提供推理服务。训练任务和推理服务层在显存分配、批处理和容错需求上差异显著，这种上下文切换在运营上颇为复杂，但在投入超过 5 亿美元的建设成本面前，双用模式在经济上是必要的。

### X 平台带来的特殊推理需求

Grok 与 X（Twitter）的深度集成，形成了与纯 API 流量截然不同的推理需求特征：

- **查询突发**：X 上的热点事件会同时触发数百万用户的查询请求。与遵循组织工作节律的 API 流量不同，社交媒体推理需求是突发且高度相关的——一条突发新闻可以在数分钟内产生巨大的并发负载。
- **实时增强**：Grok 具备对 X 帖子和网络搜索的实时访问能力，这意味着每次查询在推理之前可能需要外部检索。这在关键路径上增加了延迟，并在服务路径中引入了非确定性的 I/O 等待。
- **延迟目标**：消费级社交媒体用户对短文本补全的预期 p50 响应时间低于 1 秒。这要求对连续批处理（continuous batching）、推测解码（speculative decoding）以及面向亚秒级 SLA 调优的 KV 缓存管理进行积极优化。

### 社交规模下的推测解码

要使 3140 亿以上参数的模型在 p50 延迟低于 1 秒的条件下提供服务，通常需要使用一个较小的草稿模型（估计在 70–130 亿参数规模）进行推测解码，与 Grok 的验证传递并行运行。这一方式摊平了自回归解码的内存带宽瓶颈——每个 token 的带宽利用率提高，每个 token 的挂钟时间下降。代价是每个推理实例上需要为草稿模型额外占用显存。

## 6. 工程权衡对比

| 决策 | 收益 | 代价 |
|---|---|---|
| 单地点 10 万 GPU 集群 | 园区内同步集合通信延迟极低（InfiniBand <5 μs）；训练集合操作无广域网惩罚 | 单一地理故障点；供电与散热必须在本地解决；受限于当地电网可用容量 |
| H100 SXM5 而非 H200/Blackwell | 当下即可批量供货；比 Blackwell 规模交付提前 12 个月以上 | 放弃 H200 约 1.4 倍内存带宽提升；B200 的 FP8 性能每芯片显著更高 |
| MoE 架构（Grok-1/3） | 每个 token 约激活 860 亿参数（占 3140 亿总量）；服务阶段每 token 推理算力更低 | 训练中的专家并行开销；全对全路由延迟；比密集模型更难微调 |
| 现场自建供电 | 摆脱电网接入排队限制；支撑单地点 400 MW 需求 | 燃气轮机和电网基础设施的资本支出；许可审批和首次通电时间 |
| FP8 训练（Grok-3） | H100 上约 2 倍于 BF16 的吞吐量；激活值显存占用降低 | 需要精细的损失缩放以保证数值稳定性；2024 年工具链成熟度低于 BF16 |
| 训练/推理双用集群 | 硬件利用率提升；推理收益摊销训练资本支出 | 训练与服务上下文切换的运营复杂性；显存和网络调度存在相互干扰 |
